# Changelog

## 0.13.10 (unreleased)

- **Playwright kinds follow custom fixture definitions.** Fixture parameters
  are classified from the browser and API building blocks their definitions
  reach, including fixture-on-fixture chains. API-only fixture evidence is
  included when an E2E mapping contradicts the inferred kind. Unfollowable
  fixtures remain `unknown`; runtime proof rules are unchanged.

- **HTTP-client kind signals follow reached helpers and Playwright API
  requests (F4).** Discovery recognizes `page.request` and `context.request`
  calls through imports, attributed only to tests that call a reachable test
  helper. `fetch`/`axios` calls are detected in the test file; calls in
  imported product modules do not count as Playwright API evidence.

- **Setup-project tests never carry claims.** Discovery marks rows in projects
  the Playwright runner resolved as dependencies of other projects. A claim
  mapped to such a row is refused with the dependent project names; when the
  runner's dependency graph is unavailable, mapping behavior is unchanged.

## 0.13.9

Theme: Gateforge exists to catch fake tests. This release closes three ways a
fake E2E test could pass: API calls from test code, requests started by test
code inside the page, and tests whose code Gateforge never read. Reading
every test exposed false "page tampering" refusals of real UI tests (one
app: 169/169 tests; another: every claimed test). The tamper rules below now
let through only what is PROVEN harmless; anything unclear stays flagged.

- **Discovery: parameterized and reference-form storage-only init
  scripts are not tampers (F2).** A storage-only `addInitScript` may
  take parameters (with exactly one argument per parameter — they are
  serialized data inside the script) and may be passed as a reference
  to a locally declared function, with a body of storage calls keyed
  and valued by literals, parameters, declared constants, and inert
  builtins (`JSON.stringify`, `String`, `Date.now()`,
  `new Date().toISOString()`) under `if`/`try`/`catch` guards. Arity
  mismatches, template forms, unresolved identifiers, network/DOM
  statements, and `page.evaluate` of the same function stay tampers.
- **Discovery: an imported helper's tamper risk is attributed to the
  tests that reach it (F3).** A tamper written in the spec, or one that
  executes at import time anywhere in the import graph, still flags
  every test of the file. Otherwise the test's body — and the fixture
  chain its registration name resolves through — is followed: a direct
  call to a risky helper flags that test at the helper's tamper line,
  through transitive imports and re-exports. Helpers passed around as
  values, dynamic namespace access, and unprovable shapes keep today's
  file-wide flag.
- **Discovery: an existing `.json` import is a data module (F6).** No
  unresolved-import row, no parse, no test bindings; the spec around it
  is read. A `.json` specifier naming nothing stays a visible row.
- **Discovery: a `.js`-style import resolves to its TypeScript sibling.**
  A relative specifier ending `.js`, `.mjs`, `.cjs`, or `.jsx` names the
  TypeScript sibling of the same stem whenever the literal file does not
  exist (`.js`→`.ts` then `.tsx`, `.mjs`→`.mts`, `.cjs`→`.cts`,
  `.jsx`→`.tsx`) — TypeScript's own ESM substitution, and the rule every
  runner loader already applies. Specs importing a `.mts` helper through
  a `.mjs` specifier no longer grow a blocking `unresolved-import` plus
  a required `<unresolved-title>` row beside the instance the runner
  itself enumerates (real-app run: 92 false RUN_INCOMPLETE of this
  shape). The literal file always wins when it exists.
- **Discovery: a static call site the runner provably never registers is
  an informational note, not a required case.** The runner's list is the
  authority on what executes: when a file has listed instances but a
  computed-title call site (`dynamic-title`, or a `<unresolved-title>`
  row) has none, the row stays catalog data carrying the note "call site
  never registered by the runner: conditional or unreached" — it plans
  nothing, demands no session, and never makes the inventory incomplete
  (real-app run: conditional journey registrations produced dozens of
  these false blocks). Files the runner lists NOTHING for keep failing
  closed, and a resolved literal title the runner does not list stays a
  blocking row.
- **Discovery: the import-traversal budget is 2000 files (was 200).** Since
  0.13.9 reads every file the runner lists, a real suite (147 spec files)
  pulled 266 helper files, hit the old cap and marked the whole inventory
  incomplete (`TEST_INVENTORY_INCOMPLETE`) though nothing was unreadable.
  The cap only stops runaway import graphs; scan time was unchanged, and
  exceeding the new cap still fails closed.
- **`evaluate` is no longer a static tamper signal in chromium projects
  (F7).** In Chromium, requests started by evaluated test code are
  refused at runtime, so `evaluate` itself is no longer refused when
  reading the code: `page.evaluate`, `locator.evaluate`,
  `evaluateHandle`, `$eval`/`$$eval` stop flagging a row whose project
  the runner resolved to chromium. firefox/webkit rows keep the flag —
  the runtime rule cannot see there — as does every project whose
  browser is undetermined (fail closed). Every other tamper call
  (route, fulfill, exposeFunction, setContent, CDP sessions, non-
  storage-only init scripts) refuses exactly as before, and an
  evaluate-only helper no longer hides a later route tamper in the same
  file.

- **Discovery: every test file Playwright lists is read.** A listed test
  outside the configured source globs used to be skipped by the code scan,
  so its declared kind was accepted unchecked. Playwright's list now decides
  which files are tests; owner exclusions still apply.
- **Mapping: unreadable tests cannot carry E2E claims, and say so.** A
  Playwright-listed test whose code the scan could not read cannot be mapped
  as `browser-e2e`, `observed-e2e`, or `api-e2e`. The report's `blocking`
  list and the claim's verdict name it: "Gateforge could not read the code
  of test …" (cause `TEST_KIND_UNKNOWN`), instead of "no claim declares".
- **Discovery: follow test wrappers over the Gateforge fixture.** The
  package root and its exported `/fixture` subpath are recognized as
  Playwright test sources, through local CommonJS (`exports.X`,
  `module.exports.X`, `module.exports = { X }`) and ESM wrapper modules.
- **Discovery: prove npm aliases from package metadata.** A bare package
  alias counts as the Gateforge runner only when the root or nearest
  package manifest maps it to the exact Gateforge package, or the installed
  package metadata names that package. Unproven imports stay unresolved.
- **Discovery: join data-driven tests by call-site line.** When a test's
  title is computed at runtime, every listed instance at the scanned call
  site's exact line inherits that call site's facts; resolvable titles
  still join by title.
- **Requests started by test code inside the page are not E2E evidence.**
  Chromium fixture requests are attributed through CDP's outermost script
  initiator; page-evaluated and injected-script requests cannot satisfy
  observed transport claims. Requests without script initiators and real
  app code remain eligible. Other browsers retain existing behavior and
  report that test-code initiators cannot be distinguished. The fixture
  waits for the browser's initiator event only (at most 50 ms), never a
  fixed pause, so the app's request timing is unchanged.
- **Deliberate tightening: test-code API requests are never E2E evidence.**
  This reverses 0.13.2's crediting of Playwright API calls: requests made
  by test code go directly to the app, never through the session proxy, and
  never satisfy observed HTTP claims. Consumers whose claims came from
  API-only tests will see those claims go missing; drive the operation
  through the app's UI instead. Direct-call diagnostics cover the `request`
  fixture and `request.newContext()`; `page.request` and `context.request`
  are not credited and do not receive that specialized diagnostic.
- **pack-fastapi: preserve registration order across slash variants.**
  Merged route registrations retain their source order so ambiguous route
  attribution follows the actual framework registration sequence.
- **witness: probe composed collection adapters without `readPath`.**
  The adapter-kit's list-collection probe now exercises the adapter's
  first page even when it composes the read path internally.
- **witness: allow omitted deletion semantics for delete-disabled
  resources.** A bound adapter can omit `deletion` when the resource's
  lifecycle classification disables delete; a declared `deletion` there
  is still accepted (it must be `hard` or `archive`).

## 0.13.8

- **cli: a selected step of a serial journey selects the whole serial
  group.** A named selection narrows the supervised Playwright run to
  the mapped tests' exact `file:line` locations, so a serial journey
  whose MAPPED steps were its later ones executed without the group's
  own earlier steps — the steps that create the state the later steps
  read — and failed by construction (a real consumer serial describe of
  8 dependent steps with 3 mapped could never run green). When a
  selected test belongs to a describe in serial mode, the run now
  selects every test of that group in file order: the runner receives
  every step's location, the expected set registers every step, and
  each step's own claims are graded like any selected test's (a step
  that declares nothing contributes nothing). Serial mode is read
  STATICALLY from the spec source — Playwright's own list mode never
  exposes a suite's declared mode — and detects exactly three
  declaration forms: `test.describe.serial(...)`, a describe whose body
  calls `test.describe.configure({ mode: 'serial' })` (before or after
  the tests it governs), and the file-level
  `test.describe.configure({ mode: 'serial' })` (the whole file is one
  serial scope). A describe that declares nothing serial is never
  expanded, and an expansion never leaks beyond the selected test's own
  file or project. The run names each expansion on its output
  (`selection: added 2 tests of serial group 'journey'
  (specs/journey.spec.js)`) and the report carries an additive
  `serialExpansions` field. A full run selects everything already, a
  re-seal replays its parent's file-scoped plan, and a changed slice
  for Playwright is file-granular, so none of those print an expansion;
  members are drawn from the planned set only, so quarantined tests are
  never re-added.

- **pack-playwright: `runtime.yml trace` sets the supervised run's
  Playwright trace mode.** The generated config a supervised Playwright
  run executes under hardcoded `use.trace: 'off'`, and the consumer
  config is never loaded by design, so an owner who turned traces on in
  their own config never got a `trace.zip` — `<state>/last-failures/`
  held error contexts and screenshots but nothing to replay the failure
  from. The runtime document now declares `trace` with one of
  Playwright's six modes (`off`, `on`, `retain-on-failure`,
  `on-first-retry`, `on-all-retries`, `retain-on-first-failure`),
  validated (an unknown mode is a typed schema violation), resolved
  beside the stall and assertion bounds, and written into the generated
  config's `use.trace` — following the 0.13.6 `expectTimeoutSeconds`
  precedent. When the key is absent the generated config keeps
  `trace: 'off'` byte-identically, and a declared run's `trace.zip`
  survives into `last-failures` with the other failure artifacts.

## 0.13.7

- **pack-fastapi: a once-called registry function now orders its
  includes.** 0.13.6 deliberately left registry-function includes
  (`register_all_routers(app)` shapes) without `registration` — the
  include executes at function-call time, so no static position seemed
  provable. Real apps mount every router through such a function, which
  made registration-order overlap resolution dead code for them (0 of
  782 endpoints carried `registration` on a real consumer). When the
  call site is provable in full — the function is a plain module-level
  `def` whose include target is its own parameter, called EXACTLY once
  across the scanned set, by a top-level expression statement of the
  module that owns the `FastAPI()` argument — the expansion now joins
  that module's statement order at the call statement, and each
  function-body TOP-LEVEL `include_router` statement carries the
  flattened order like a written include (statement order inside the
  function breaks ties between same-position expansions). The order
  sequence stays the real registration sequence: the app module's
  module-level statements in source order with the call expanded in
  place, so an include written after the call and routes on the app
  itself order after the whole expansion. Everything else fails closed,
  exactly as before: a second call site anywhere, a call nested in a
  statement or inside another expression, a call from a module other
  than the app owner's, a chained helper hop, and an include nested in
  `if`/`elif`/`else`/`for`/`while`/`try`/`with`/`match` mount without
  `registration` — order-uncertain blocks are skipped, and the relative
  order of the provable routes stays correct (the resolver never
  resolves an overlap that involves a candidate without registration).

## 0.13.6

- **A literal-vs-parameter route overlap resolves by the framework's own
  registration order.** `resolveHttpRoute` marked an observed exchange
  `ambiguous` whenever more than one inventoried route matched
  method+path, so `GET /x/actions` — matching both the literal
  `GET /x/actions` and a `GET /x/{event_id}` parameter route — could
  never satisfy its claim even when the app really serves the literal
  route: Starlette, and therefore FastAPI, matches routes in
  REGISTRATION order (each router's routes copy at its `include_router`
  call, depth-first in call order, decorator source order within a
  router; the first full match — path AND method — serves). The FastAPI
  detector now proves that order statically: every endpoint it can place
  carries `registration: {scope, order}` (`scope` is the serving app's
  uvicorn-style `module:var` identity, `order` the 0-based position in
  the app's flattened registration sequence) plus `typedPathParams: true`
  when the path string carries a typed convertor (`{n:int}`, `{p:path}` —
  a convertor matches narrower than the canonical single-slot shape; a
  function annotation such as `event_id: UUID` never affects routing and
  is correctly ignored). The compiled inventory carries both through to
  the resolver, which resolves a multi-match overlap ONLY when every
  matched route carries a registration in the SAME app with distinct
  orders and no route ordered ahead of the winner is typed — the
  smallest order then grades like any unique match (match for its own
  obligation, mismatch for every other endpoint's). Routes whose
  position is not statically provable — appended to a router after it
  was included, declared inside a function body, reachable from more
  than one app, mounted through a call-time (registry-function)
  include — carry no registration, and other packs emit none, so every
  overlap they produce stays `ambiguous` exactly as before.

- **Supervised runs honour an owner-declared assertion timeout.** The
  generated config a supervised Playwright run executes under set no
  `expect.timeout`, so an assertion without an explicit timeout got
  Playwright's 5-second default even when the consumer's own config
  raised it — and the consumer config itself is never loaded, so the
  value was unreachable. `runtime.yml expectTimeoutSeconds` (integer,
  1–600) is now carried into the generated config as `expect.timeout`
  (`test-gates` and the commit hook alike). When the key is absent,
  nothing is emitted and Playwright's default stands.

- **A red selected run keeps its Playwright failure artifacts.**
  `test-gates --result-only` without `--witness-url` ran in a temporary
  state directory and deleted it with everything Playwright wrote for a
  failed test (error context, screenshots), so a test that failed only
  under the supervisor could not be diagnosed. The artifacts are now
  copied to `<state dir>/last-failures/` (replaced every run, removed
  after a run without failures) and the path is printed on stderr.

- **A blocked transport claim names the call that blocked it.** When a
  test's witnessed session held an exchange of another endpoint (a login
  before the real call) and the obligation's own call was blocked (a
  literal-vs-parameter route overlap, or a non-2xx status), the verdict
  reason named the unrelated exchange ("uniquely matches route POST
  /auth/login") instead of the real cause. Reasons about the obligation's
  own route now outrank exchanges of other endpoints, inside one observed
  session and across sessions. Verdicts are unchanged; only the reason
  text differs.

## 0.13.5

- **Supervised runs honour a project's declared test timeout.** The
  generated config the supervised run executes under always set a 60 s
  per-test timeout, so a test that needs longer under the consumer's own
  configuration (`timeout: 180_000`) failed with "Test timeout of 60000ms
  exceeded". Discovery already runs `playwright test --list` and reads the
  timeout the runner resolved for each project from its JSON report; that
  number now travels with the planned project and is written as that
  project's own `timeout`. It is data only: the consumer config is still
  never loaded. The 60 s default is a floor, because Playwright reports its
  own 30 s default for a project that declared none, and a consumer who
  never set a timeout keeps today's 60 s. A project that reports no
  timeout, `0`, or a non-finite value also keeps 60 s.

## 0.13.4

- **A suite that mixes the fixture's `test` with Playwright's own runs in
  file order again.** Since 0.13.0 the fixture replaced Playwright's
  worker-scoped `browser` to open a debugging port for page observation.
  Playwright schedules tests whose runners differ in a worker-scoped
  fixture in separate worker groups, so every fixture test ran after the
  plain ones, and a suite whose later tests relied on state an earlier
  fixture test created failed after upgrading. The replacement is now
  registered only when the supervisor enables page observation (the only
  reader of the port). With page observation on, a mixed suite still runs
  in two groups: take `test` from the fixture everywhere to keep one
  order.

## 0.13.3

- **Hooks on the fixture's `test` receive their fixtures again.** 0.13.2
  wrapped `beforeAll`/`beforeEach`/`afterEach`/`afterAll` to keep hook
  setup traffic uncredited, but the wrapper hid the hook's parameter list
  from Playwright, which picks a hook's fixtures by reading it. Every
  `test.beforeEach(async ({ page }) => …)` got an undefined `page`. The
  wrapper now reports the consumer's own callback to Playwright, and a
  titled hook (`test.beforeEach('title', fn)`) keeps its title.

- **Hook setup traffic stays uncredited on a suite's own runner too.** A
  suite that builds its runner with `test.extend(...)` on the fixture's
  `test` got Playwright's unwrapped runner back, so a `request.newContext()`
  call inside its `beforeEach` rode the running test's session proxy and
  was credited as test traffic. `extend` now returns a runner whose hooks
  are tracked the same way.

## 0.13.2

- **API tests are witnessed: the Playwright APIRequestContext now rides the
  session proxy.** API specs that use `request` (the fixture),
  `page.request`/`context.request`, or `request.newContext()` never pass
  `page.route`, so the session proxy never saw their exchanges and their
  endpoint traffic could never be witnessed. The Gateforge fixture now
  wraps those contexts (additive; without a witness wired, behavior is
  byte-for-byte today's): every call whose resolved URL carries the app
  origin is rehosted onto the test's session proxy — the same host swap
  the page channel performs, with path, query, headers and body
  untouched; other origins pass through, and a same-host or loopback
  other origin is reported like an unrouted page origin. The fixture
  module exports `request` next to `test`/`expect`; its `newContext()`
  resolves the session per call from the running test and goes straight
  to the app inside worker hooks and module scope, so setup traffic stays
  uncredited. Kind inference no longer proposes `api-e2e`/`unit` from a
  Gateforge-pack import, so `tests mark --kind observed-e2e` is
  declarable for exactly the tests the channel witnesses. The observation
  proxies listen on every loopback address the app hostname resolves to
  (a name such as `localhost` answers both `::1` and the IPv4 loopback),
  so a Node-side client whose resolver picks the other family still
  reaches the session proxy.

- **The sweep progress line names the requests that refused a page.** A
  page printing only `refused PAGE_API_UNSETTLED (782 ms)` left nobody any
  wiser about WHICH request never settled. A refused visit now keeps its
  culprits — the additive `unsettledRequests` field on the visit and in
  the `page.observed` payload (both the observed and the swept channel):
  un-superseded failures with their real browser error text, then
  still-open requests as `outstanding`, capped at five, urls without
  query — and the per-page progress line appends them:
  `page 5/56 erp /billing/documents -> refused PAGE_API_UNSETTLED (782 ms): GET /api/v1/foo net::ERR_ABORTED; POST /api/x outstanding`.
  A `PAGE_API_ERROR` line names the refusing response
  (`GET /api/y -> 500`, honoring the grader's anonymous-401 exemption)
  instead of printing only the reason code.

- **`tests suggest --from-run`: suggestions from a witnessed run's own page
  observations.** A witnessed run already records, per test, every API
  request each page made; the suggestion engine no longer has to guess from
  names. The witness now stamps each recorded exchange with its method (the
  additive `method` field on `page.observed` payloads' `apiStatuses`
  entries, in both the observed and the swept channel), and
  `gateforge tests suggest --from-run [--run-dir <dir>]` reads that ledger
  from the run state directory, matches every same-origin app API exchange
  (status under 400) against the current endpoint inventory with the
  shared router semantics — a literal segment beats a parameter; more than
  one equal match is reported as ambiguous, never guessed — and prints,
  per observation obligation no test declares and the run did not satisfy,
  the tests that exercised it, the evidence lines
  (`METHOD path -> status (run <runId>)`), and the exact
  `tests mark --kind observed-e2e` command. Advisory only: nothing is
  written. Exchanges that matched no endpoint (usually an app bug) and the
  ambiguous ones are listed separately with the test and path.

- **A `.gateforge/runtime.yml` that `.gateforge.yml` never references now
  warns instead of being silently ignored.** The supervised runner forwards
  only the environment variables listed in that file's `envAllowlist`, and
  only when the config declares the file with a `runtime:` key. A
  `runtime.yml` alone was read by nothing, so a witnessed run failed on
  missing variables with no hint why. `check`, `next`, `test-gates` and the
  commit hook now print one warning naming the missing `runtime:`
  declaration.

- **A second `tests mark` for the same test adds to its claims instead of
  replacing them.** The first mark's obligations survive; the resulting
  claim list is printed. A repeat that declares a different `--kind` or a
  different `--category` set is refused, naming both and the sidecar edit
  that changes them. The repeatable `--obligation <id> --obligation <id>`
  form is documented in QUICKSTART §5 and REFERENCE.

- **`gateforge explain` accepts the obligation ids other commands print**
  (`<resourceId>:<contract>`, including transport/http ids such as
  `…:http:request-observed`): it resolves the obligation's resource, shows
  its trace, and names the requested obligation in the obligation list. A
  truly unknown target still reports `no discovered resource matches`.

- **init's no-terminal notice names the edit that works.** It now says to
  set `mode:` in `.gateforge.yml` (per preset: `warn`, `changed`,
  `strict`) instead of "re-run with `--preset`" — that re-run exits 2,
  because init never rewrites an existing config. QUICKSTART §2 says the
  same.

- **`tests discover` exits with its own verdict when the output reader
  goes away.** Reading a large catalog through `| head` (or any reader
  that closes early) killed the process with an unhandled `write EPIPE`
  and exit 1 after discovery had already succeeded — the same repository
  exited 0 on one run and 1 on the next. The exit code is now always the
  command's own.

- **The test scan parses only script extensions, never JSON files.** A
  spec importing a translations `en.json` flooded the catalog with
  thousands of parse-error rows (18,658 on one real app) because the
  import edge pulled the JSON document into the JavaScript parser. The
  scan now resolves only `.js .cjs .mjs .ts .cts .mts .jsx .tsx` files.

- **init recommends `@gate-forge/pack-react-router` when the app uses
  React Router.** Any scanned `package.json` — root or nested like
  `frontend/` — declaring `react-router` or `react-router-dom` in
  dependencies or devDependencies recommends the pack, with the declaring
  file as the printed reason.

## 0.13.1

- **Frontend detector: a trailing query-string hole is read as a query, not a
  path segment.** Calls written like
  `` `.../meters${qs ? `?code=${code}` : ''}` `` (also the `&&`, `|| ''`, and
  const-bound forms, including function-local `const`) used to render their
  unresolved hole as a positional slot glued to the last path segment
  (`meters${}`), so the call failed to join its backend route and was reported
  unwired. When the template's last hole provably evaluates only to query or
  fragment text (empty, `?…`, or `#…`), it now renders as a bare `?` and
  normalization strips the query, so the call joins its route. Anything not
  provably a query suffix — a hole mid-path, a trailing path value, a branch
  starting with `/` — is unchanged.

- **The post-suite page sweep can now run past five minutes.** The
  supervisor's call to the witness used Node's global fetch, whose fixed
  300-second internal header/body timeout aborted every sweep budgeted for
  longer than that, reporting `fetch failed` no matter what deadline the
  sweep itself had computed. The supervisor client now performs its HTTP
  calls directly with `node:http`/`node:https`, so the computed budget (base
  timeout plus the per-page allowance) is the only deadline. Error types,
  messages, and fail-closed behavior are unchanged; a budget shorter than a
  slow answer still aborts with the same typed error.

- **A storage-only init script no longer refuses page proof.** A spec or
  helper calling `page.addInitScript(() => localStorage.setItem('lang',
  'en'))` (also the block form, `sessionStorage`, `removeItem`/`clear`,
  optional `window.` receiver, and the `context.addInitScript` form) was
  reported as a page-observation tamper risk and refused page-level proof.
  Such a script only sets storage keys the witness's independent observer
  can see, so it is no longer a tamper; the scan continues past it, and a
  real tamper later in the same file (a route interception, `window.fetch`
  reassignment, a template or non-literal value, extra arguments, or a
  string/path script) is still reported at its own line.

- **A page may keep a live connection open (`pages.liveChannels`).** A page
  whose app holds a long poll, a WebSocket, or a server-sent-events stream
  open forever used to burn the whole visit settle budget and refuse the
  page with `PAGE_API_UNSETTLED`. Declaring the stream's path prefix under
  the new controller-held `pages.liveChannels` configuration (same rule in
  both proof channels) makes such a request a live channel: it never counts
  as app data evidence, never holds the settle wait, and never refuses the
  page by itself; the visit payload lists what stayed open (`liveChannels`,
  count + paths). WebSocket upgrades on the app host and `text/event-stream`
  responses are live channels by protocol, with no declaration needed. An
  undeclared open request still refuses the page exactly as before.

- **A rejected audience session stops that audience's page sweep.** When an
  audience with a session lands on one of its declared login routes on the
  first visited page (the usual rotating-refresh-token case: the suite's run
  consumed the session the file carried), that page is graded as today and
  every remaining page of the same audience is refused without visiting it,
  with the new `PAGE_AUDIENCE_SESSION_INVALID` reason. The records still
  issue, the sweep payload says each page was not visited and why, and one
  log line asks for a session file the suite does not consume. Session-less
  audiences are unaffected.

- **The page sweep reports progress per page.** Each visited page emits one
  line as its visit finishes — `page 3/12 tenant /orders -> proven (1234
  ms)` — so a killed sweep keeps the lines it already earned instead of
  staying silent for minutes. `--progress off` asks for none.

## 0.13.0

- **Pages-family adoption for already-adopted repositories (0.13.0).**
  `gateforge adopt --family pages` revises an ALREADY-adopted repository —
  the one owner-approved exception to the one-bulk-add invariant, scoped to
  a named family. Preview by default (nothing written); `--confirm` performs
  ONE atomic write to the existing `.gateforge/baselines/adoption.json`: a
  dated, commit-referenced `families.pages` marker recording EVERY page
  obligation discovered at that moment (proven pages included), with only
  the then-missing/unproven page fingerprints marked `forgiven`. Receipt
  writes are validated and then atomic (same-directory temporary file +
  rename): a failed or interrupted write leaves the previous receipt
  intact, never a truncated one. The

  `PAGE_API_UNSETTLED`. Both proof channels — the browser tests' observed

### Added

- **Owner-declared business rules, test-type agnostic (0.12.0).** The owner writes the
  product's rules down in the `rules:` section of `.gateforge/classification-policy.yml`
  (`gateforge init --rules` adds a commented example; a repository without the section is
  byte-identical to a release without the feature). Each rule names the test type that must
  prove it — `e2e` (default) or `pytest` — and splits into CASES (the observable
  consequences; a rule without `cases:` has one implicit `default`). A case is mapped by the
  claim id `business-rule:<ruleId>/<caseId>` through the ONE mapping resolver
  (`tests mark --rule <ruleId>/<caseId> …`): staleness, ambiguity, quarantine and
  inferred-only behave exactly as for obligations, and rule bindings never enter any
  obligation set, graded obligation array or receipt coverage list. A declaration is never
  proof: the case is graded by a pure evaluator over the sealed run's own facts — `e2e`
  requires the mapped test to have run, passed, and carry witness evidence attributable to
  its own session (engine `ui.action` anchor, or a witnessed `http.request` exchange of the
  session for `observed-e2e`); `pytest` requires the witnessed suite of the sealed run. Every
  mapped test of a case must deliver the proof (a green sibling never forgives a red one), a
  mocked spec never proves an end-to-end rule, a test outside the run's graded slice is
  reported `unproven` — never satisfied, never silently absent — and rule findings are
  run-wide, never diff-scoped away. `enforcement: advisory` (requires `advisoryReason`) rides
  the report's existing advisory channel every run, out of `blocking` and out of the exit
  code. The gate surfaces: `check` blocks (or advises) per case; `check --require-e2e` and
  `test-gates` grade from the sealed receipt's authorized records; the json report carries an
  additive `businessRules` section naming every graded case with its status and proof
  channel; `gateforge next` ranks the four rule causes with the coverage band and prints, per
  missing case, a starter test (the type table picks the Playwright-fixture or witnessed-
  pytest template) plus the exact `tests mark --rule` line. An unknown `subject` is a
  configuration error (exit 2).

### Fixed

- **A fresh adoption can push again: an empty optional config directory is digested exactly like an absent one.** `gateforge init` creates EMPTY `.gateforge/adapters/` and `.gateforge/waivers/`, and Git cannot carry an empty directory — so the committed tree has neither, while the live worktree has both. The trusted-policy digest entry list and the input snapshot each gave the two shapes DIFFERENT absence markers (`(no .mjs adapters)` vs `(missing adapters dir)`, `absent:<dir>/(empty)` vs `absent:<waiversDir>/(missing waivers dir)`), so the pin an owner minted over their adoption commit (`enforcement pin`) was a digest the pre-push/CI candidate-commit gate never computed for that very commit: every push blocked `ENFORCEMENT_UNTRUSTED`, and re-pinning could not converge. Both surfaces now emit ONE absence marker per optional directory (nested empty directories are invisible, exactly as Git sees them), which also retires the worktree-shaping of materialized candidate checkouts (`mirrorEmptyConfigDirs` is gone — the bytes of the tree under test are the whole story). A repository with a missing directory, or with tracked adapter/waiver files, keeps today's digest byte-for-byte; only a repository that pinned over empty directories re-pins once, and from then on every surface agrees.

### Changed

Fail-open as before: a budget-cut graph attributes nothing.
- **A directory in a runtime command is no longer a "runtime input" that refuses the whole run.** The reader that resolves a `runtime.yml` command's argv tokens accepted ANY path that existed, and a directory exists: `npm ci --prefix e2e` or `docker compose … --project backend` therefore bound a directory as a runtime input, and the input snapshot — which exists precisely to bind FILE bytes — rejected the run with `unsupported input snapshot: input snapshot rejects non-file input 'e2e'` (exit 2 on `check --changed`). 0.10.1 had no runtime inputs at all, so an upgrade turned a green repository red for a directory the owner never declared. The reader now stats each token and accepts a regular file only, exactly as its name says; a file token is still a runtime input and keeps its attribution, the scope expansion and its place in the snapshot.
- The files the staged runtime document NAMES — a `scripts/e2e/*` runner, a compose override, an `.env` in `env_files` — are RUNTIME inputs: attributable, scope-expanding, and part of the input snapshot, so a sealed receipt binds their bytes and an UNDECLARED stack file still blocks. They are deliberately NOT added to the owner-approved policy digest: a port or a base URL changes far too often to justify a re-pin, so binding them through the snapshot is the honest place. A declared file that does not exist yet is recorded as an explicit absence, so creating it later changes the receipt's identity.
- The static test catalog no longer turns a file the runner's OWN configuration disclaims into a blocking inventory gap. A spec matched by a project's `testIgnore`, or sitting outside every project's `testDir`, becomes no catalog row at all, so one folder of dead duplicate specs can no longer make a whole repository unsealable (`inventoryComplete: false` → `TEST_INVENTORY_INCOMPLETE` on every run). A file INSIDE a declared `testDir` that no selection claims is a possibly misplaced test and still blocks. Every scope read stays fail-open: a selection that cannot be read faithfully claims every file.
- Deleting test files no runner ever collected is no longer reported as an unclassified product change. A deletion cannot introduce behaviour, and a file no runner collects is not a test file, so it neither expands the evaluation scope nor blocks. Deleting a file a runner DOES collect keeps every other rule.
- `gateforge test-gates` honours the whole-run budget its own `runtime.yml` declares. `executionTimeoutSeconds` was read by the commit hook and ignored by the command it is written for, so a repository declaring 3600 s was killed at the 30-minute default. An explicit `--run-timeout-min` still wins; an unreadable runtime document keeps the default bound.
- `gateforge test-gates` names the cause when its policy digest disagrees with the owner-approved pin. It digests the WORKING TREE while `check --staged` digests the STAGED INDEX, so while a policy input is modified-but-unstaged the two compute different digests and no single pin satisfies both — and the remedy the commit gate prints was the command this refusal blocked. The diagnostic now names the differing policy inputs and a remedy that clears it.
- `gateforge enforcement pin` prints the command that loads the file it just wrote. Every command reads the pin once at process start, so a shell holding the previous digest read exactly like "my pin did not take".
- **Adoption mode no longer accepts the receipt and then exits 1 anyway.** The scoped receipt was accepted, but the adoption commit still failed: its gate-defining inputs (manifest, runner configuration, mapping sidecar) expand the evaluation to full scope, so every UNTOUCHED pre-existing obligation without evidence graded blocking `missing` under `strictE2E` — and the adopted baseline that covers exactly that debt was re-graded too, because the forgiveness required a change set of Gateforge-owned policy inputs ONLY, which is a set the commit that WIRES the gate can never be. The baseline now also survives the re-grade when the change set is product-behaviour-neutral (every changed file is a policy input, a gate-defining input, a catalog test file, test infrastructure, a runtime-declared input or `docs/**.md`, and NO discovered resource's source is in it), the candidate IS an adoption commit (still computed from the base revision — no flag, no config key), and the owner pin is enforced on the same condition as before. One changed product source, one commit after the first, or one missing pin denies all three and the debt blocks exactly as before. An owner waiver is still never forgiveness.
- **A worktree run and a worktree check are ONE input identity again.** `gateforge run` sealed its receipt with the declared `prepare.reuse` roots bound in the gate context, but a standalone `gateforge check --require-e2e` recomputed the identity WITHOUT them — so in every repository whose `runtime.yml` declares reuse roots, the pair a consumer is told to run (`gateforge run`, then `gateforge check --require-e2e`) failed closed on an UNCHANGED worktree with `evidence-context: durable attestation inputDigest does not match the current input snapshot`. The rule — an explicit digest, else the declared roots, else nothing — now lives in ONE resolver (`resolveRuntimeReuseDigest`) that `computeInputSnapshot` calls itself, so the run, `check`, `next` and `tests` cannot disagree about which dependency bytes the receipt is sealed over, and the local copy the run kept is gone. The staged surfaces still hand over the digest `prepareRuntime` bound AFTER the links were made, so the commit gate keeps its own value; one changed byte inside a declared reuse root still moves the identity and refuses.

### Added

- Config key `project.paths.testTooling` in `.gateforge.yml`: globs the owner asserts are test/developer tooling. The import-graph fix above cannot see a `scripts/e2e/run.sh` that only `package.json` scripts name — nothing imports it and no runner configuration names it — so the owner declares it, and the declaration is deliberately weak: a matching changed file EXPANDS the evaluation scope exactly like test infrastructure (never proven by a slice of the suite) and is never `CHANGE_UNMAPPED`. ### Added

- `gateforge migrate [--confirm]`: moves owner declarations out of their own files into `.gateforge.yml`. Preview by default (exact diff of `.gateforge.yml` plus the files that would be deleted, nothing written, exit 0); `--confirm` writes the `evidence.exclude` block as text, deletes the old files, and prints `policy inputs changed: re-pin the approved digest (gateforge enforcement doctor)`. Both old files are validated with the existing loader rules; an `evidence:` / `exclude:` / `docs` shape the writer cannot extend safely is refused by name and nothing is written. Idempotent: nothing to migrate prints `nothing to migrate` and exits 0. One step registry (detect + preview + apply), so later owner-file consolidations only add a step.
- Config key `evidence.exclude.docs` / `evidence.exclude.cache` in `.gateforge.yml`: strict objects, arrays of non-empty strings; unknown keys and empty strings fail the config load like every other key.
- `gateforge enforcement pin --pin-file <path> [--confirm]`: writes the owner-approved policy digest of the STAGED candidate into an env file OUTSIDE the repository. The flag is `--pin-file`, NOT `--env-file`: Node consumes `--env-file <path>` (and `--env-file-if-exists <path>`) out of argv itself, even after the script path — it reads the file and exits 9 on a missing one, so the CLI never runs. The digest is computed through the same frozen-index + isolated-checkout path `check --staged` gates on, so the pin can never approve a revision the commit gate never digests. It refuses a policy input that is not fully staged (naming the file), any path inside the repository (the pin must live outside the candidate — a candidate-controlled file cannot approve policy), and a symlink or non-regular file. Preview by default; `--confirm` replaces exactly the `GATEFORGE_APPROVED_POLICY_DIGEST=<hex>` line, drops a duplicate assignment, leaves every other line untouched, never prints another line of the file, and writes mode `0600`.
- `gateforge enforcement doctor` reports `policy-inputs-vs-HEAD`: the trusted-digest inputs whose STAGED bytes differ from HEAD, named one by one (`policy inputs changed since HEAD: .gateforge.yml, .gateforge/runtime.yml`). A whitespace-only edit counts — it moves the digest. The inputs come from the ONE function that yields the digest entries, and both revisions are compared by presence and bytes.
- `gateforge enforcement doctor` reports `approved-digest`: the provisioned pin compared with the STAGED digest, as `matches staged`, `does NOT match staged (changed inputs: …)` (or `no policy input changed in the staged index — the pin predates an already committed policy change`), or `absent`. Both new rows read the same staged entry list the digest is computed from, so a named input and the digest verdict cannot disagree.
- `gateforge enforcement doctor`'s `policy-inputs-staged` row no longer misses an unstaged policy input that is the FIRST changed path: the porcelain listing is read raw, because the trimmed `git status` output drops the leading status column of the first line.

### Fixed

- A tag that declares NO operation keeps its full weight on a transport obligation. `@crud(tenant.accounts)` names the resource and stops there; the route-method gate exists to stop `@crud(tenant.accounts:create)` answering a `GET` route, not to discard a tag that never named a verb. Such a tag is scored as explicit-tag evidence again (and can answer `new test needed: no`), where it had dropped to `unverified`.

The witness now takes one snapshot of the session's watermark-filtered, deduplicated exchanges before the claim loop, so a `persistence:*` claim's single-use consumption of a shared exchange can no longer empty a transport record that follows it (a false "no HTTP exchange passed through this session's observation proxy" blaming the fixture page for a request that did traverse the proxy). Persistence-vs-persistence consumption is unchanged: one exchange still credits at most one persistence claim.
- `gateforge tests suggest` no longer ranks a candidate on a substring, and a tag's operation text is not prose. Resource tokens are matched WHOLE-WORD (title path words; file path segments split on `/ . _ -`), and a generated resource id contributes only its NAME: the plane (`tenant`), the transport (`http`), the method (`get`), route furniture (`api`, `v1`), the `param` marker that stands in for a `{route_param}` and the trailing id hash are structure, not names. A row the runner never enumerated (`reconciliation: static-only`, e.g. a Vitest jsdom suite inside a Playwright-configured repository) is never offered as a test to mark — it can never produce the witnessed evidence a mark promises. And when every remaining candidate mocks the system under test, the obligation is not satisfiable by reuse: the report prints `new test needed: yes`, keeps listing the mocked rows as context, says why (`only mocked candidates`), and prints no `tests mark` next action for them.
- Mock detection no longer stops at the test body. A spec that calls `await page.route('**/api/v1/notifications*', …)` from a FILE-SCOPE helper every test invokes carried no mock signal at all, so `tests suggest` offered it as reusable proof of a request the app never served. Interception is now a file-level fact — any `<x>.route(…)` (`page.route`, `context.route`, …) or `route.fulfill(…)` anywhere in the spec — and it feeds the same `mock` signal for every test in that file. A folder segment named exactly `mocked`, `mock` or `mocks` gives the same signal by placement (a segment merely CONTAINING `mock`, such as `mockery`, is a helper folder and never does; nor does a FILE named `mock.spec.js`). Such rows are never offered as proof: when they are the only candidates, the obligation reports `new test needed: yes` and no `tests mark` next action.
- A Playwright config with a top-level `testMatch` and no `projects` array resolves to the runner's implicit project, whose resolved selection the project-graph reporter used to skip — leaving the catalog with no file scope at all, so every statically found file looked like this runner's own test. - A candidate must now be DISTINCTIVE and of the right CHANNEL. An operation word (`read`, `get`, `list`, `create`, …) is never a resource token — `read tenant.accounts through UI` is evidence about no resource in particular — and one word is counted once, so a resource token that is also a route segment no longer scores twice (the stronger signal stands). A row whose only evidence is a `real/` folder, an operation word or a mock signal is not a candidate at all. And for an observed-e2e contract (`http:*`, `crud:*`, `persistence:*`) a `unit` suite is never offered: it drives no app and can never witness the claim. An obligation nothing distinctive matches now reports no candidate and `new test needed: yes` — previously it offered unrelated tests and a `tests mark` command that could never produce evidence.
- `tests suggest` (and `tests explain`) now answers the reuse question with THREE honest values instead of a boolean. `yes` means nothing can be reused: no candidate survived resolution, or every candidate mocks the system under test. `no` is a claim the run can PROVE — the `#1` candidate is an unmocked e2e row and more than one signal supports it (an explicit tag naming this resource, or a resource-token match together with a file that names the obligation's route). Everything between is `unverified`: a candidate exists, reuse may well be right, and a name in common is not proof the test drives that request. Appending to a config whose items sit at indent 0 previously produced invalid YAML; that case now parses.
- The approved-policy mismatch block now carries BOTH full 64-hex digests — `(candidate <digest>, approved <digest>)` — so an owner pinning the value `gateforge enforcement doctor` prints can see exactly which policy revision the candidate computed versus the approved one, instead of only the generic reason.
- `gateforge enforcement doctor` gains a `policy-inputs-staged` row: the commit gate digests the STAGED bytes of the trusted policy inputs while doctor's digest is computed from the working tree, so an unstaged policy edit or an untracked policy file now warns with the differing paths and the `git add` action (ok when the index matches the working tree; unknown when no usable Git inventory).
- A staged-candidate test-discovery failure (e.g. `playwright --list produced no readable reporter JSON ... Cannot find module '@playwright/test'`, exit 2 — the candidate checkout holds tracked files only, so its dependencies are absent) now appends one hint line when the runtime document declares no `prepare.reuse` roots: declare the dependency directories in `.gateforge/runtime.yml` (`prepare: { reuse: [node_modules] }`, see REFERENCE "Staged runtime"). `check --staged` and `pre-commit` both carry the hint; a declared reuse root suppresses it.
- The `.gitignore` engine-state block keeps a setup commit product-behavior-neutral on the staged gate too: `check --staged` and pre-commit now classify policy inputs against the base revision resolved in the user's repository (the isolated checkout's HEAD is the staged tree, not the base), so a setup commit that also carries the `.gitignore` block `init` appends no longer re-grades the adopted E2E debt as blocking under strictE2E. A `.gitignore` line outside the managed block still blocks (fail closed).
- `gateforge init` prints one note at the start of a run in a repository with commits when the install itself (package.json or a lockfile) is still uncommitted: commit the install on its own BEFORE the setup files — a setup commit that also changes dependencies is a product change and under strictE2E re-grades the adopted E2E debt as blocking. The note never refuses and never changes the exit code.
- `gateforge adopt` no longer downgrades the commit hook a strict `init` wired: `adopt` reads the gate args the generated hook already records (a `check --staged` hook after `init --preset strict`) and re-wires with exactly those args, instead of silently rewriting the hook to the changed-scoped default (`check --changed`) — which made the commit gate judge the working tree instead of the staged bytes. A repo with no generated hook keeps the default.
- A `PLANE_CONTRADICTION` that includes the mirrored operational `global` assertion — a `.gateforge/planes.json` rule covering a router file that also holds health/readiness probes — now explains itself: the detail says health/readiness probes are global on their own, names the router file to answer `global` for when none of its routes serves business data, and offers moving the probes to their own router file. The block stays `PLANE_CONTRADICTION`; every other behaviour is unchanged.
- A Vitest config that spreads Vitest's own defaults — `exclude: [...configDefaults.exclude, '**/tests/e2e/**']`, the idiom the Vitest docs recommend — is read as data again. The spread made the whole Vitest file selection unreadable, so every Vitest test file had no owning runner, became an unresolved catalog row, and kept `inventoryComplete` false, which alone prevents a receipt from ever being sealed. `...configDefaults.include/exclude`, a bare `configDefaults.exclude`, and `defaultInclude`/`defaultExclude` expand to Vitest's documented defaults — only when imported from `vitest/config` or `vitest` in the same file; any other spread still fails open as before.
- The setup guides (`QUICKSTART.md`, `CONNECT-YOUR-PROJECT.md`) open with one explicit order: commit the install first, then init → plane answers → adopt → `prepare.reuse` → stage every policy file → pin the digest last → commit only Gateforge's own files; product changes follow in their own commits. Plane definitions with examples, and how to answer infrastructure routes (health and readiness probes are already `global`).

## 0.9.0

### Upgrading from 0.8.x

No configuration change is required and no new option is on by default. This release changes what the engine SEES on an existing repository, so counts and obligations can move in both directions after upgrading: run `gateforge discover` first, then `gateforge check`, and re-approve the policy digest if any Gateforge-owned setup file changed. Steps, what can appear or disappear and why, and the owner decisions this release asks for: `packages/cli/guides/UPGRADE-0.8-to-0.9.md`. Set every direct `@gate-forge/*` dependency (and every `overrides`/`resolutions` entry and `npm:@gate-forge/…` alias) to `0.9.0`, or npm stops with `EOVERRIDE`.

### Gate correctness

- `check --staged` now reads the STAGED bytes for in-process packs. Several detectors resolved the repository root and their config documents when the module was imported, which the CLI does at startup — before `check` moves the process into the candidate checkout — so the pre-commit gate graded the working tree: a staged file whose unstaged copy was valid (or broken) produced the opposite verdict from the commit. Every in-process pack now resolves its root and its configuration documents at DISCOVER time, so the gate judges the bytes it is about to commit. The staged gate and a plain `check` on the same bytes now agree.
- Untracked-and-gitignored files leave the scan. A working copy that holds generated output — a Playwright report bundle, a local cache — was walked like committed code, and every call inside it became detector evidence: hundreds of `FRONTEND_CALL_TARGET_UNRESOLVED` entries on a dirty working copy that a clean clone of the same commit never produced. The scan now skips exactly what Git reports as untracked AND ignored, so a clean clone and a dirty working copy of the same commit describe the same repository. A TRACKED file matching an ignore pattern is still scanned (Git never reports a tracked path as `--others`, so that follows from Git's own semantics), a nested `.gitignore` counts, the operator's global excludes file does NOT (results must not depend on the machine), and outside a Git work tree nothing is skipped, so behaviour there is unchanged.
- The receipt identity does not move with it. The input snapshot still hashes a deliberate SUPERSET of what the scan reads, so a gitignored configured input still moves the receipt digest — the conservative direction, and the one `check --out` relies on when it refuses an output path that would hide a declared input. The two scopes are separate, named functions (`expandScanPaths` for detector input, `expandIncludePaths` for identity) so neither can narrow the other by accident. Every enumeration of detector input in one run — the pipeline, `init`'s table-source pass and the route-folder plane questions — now uses the same scan scope.
- Gateforge's OWN setup files are policy inputs. The config, policy, classification, behavior and runtime documents, the exclusion declarations, the mapping sidecar, the adapter/waiver/baseline/quarantine records, the generated gate wiring (hook script, CI job templates, `GATEFORGE.md`, the overlay-proof README, the engine reference) and your CI/pre-commit config *while they still carry Gateforge's managed block* are governed by the approved policy digest, not treated as unmapped product changes: they are never `CHANGE_UNMAPPED`, a change set containing only those files cannot change product behavior, and so the `init` → `adopt` → first commit path passes `check --changed` without `--no-verify`. Integrity is unchanged: they are inside the policy digest, a change to one needs your pin re-approved, and a mismatching pin still blocks. REMOVING the gate job from your CI config, or the entry from `.pre-commit-config.yaml`, is not a policy input and goes back to blocking.
- Adopted debt stays forgiven across a setup commit under `strictE2E`. The adopted baseline is a recorded, shrink-only statement of pre-existing debt, not a risk acceptance, so it survives the strict-E2E re-grade while a change set is provably product-behavior-neutral (Gateforge-owned policy inputs only). The forgiveness is granted only when the owner has pinned the policy revision governing those files; with no pin, reporting is unchanged (adopted debt is re-graded as blocking). An owner waiver is never forgiveness here.
- `CHANGE_UNMAPPED` names the step that can actually attribute the file. It used to print `gateforge explain .gateforge/behavior.yml` for a file `explain` answers "no discovered resource matches" — a loop that could never end. The remediation now names the attribution step and what to do with the answer.

### Adoption on an existing repository

- `gateforge init` on a repository that already has code says so and names the way through the debt it will report on day one: `gateforge adopt` records today's findings as forgiven, shrink-only, and still blocks an adopted E2E obligation under `strictE2E` as soon as a change touches it. A fresh, empty project never sees that block. `adopt --help` now documents the baseline, its shrink-only property and the strict-E2E re-entry, and the README command table lists the command.
- `init` adds Gateforge's own engine state to `.gitignore` (`.gateforge/test-gates/` — the run catalog, plugin caches, receipts and history the engine regenerates on every run). Without it the first `git add -A` stages the run cache and the gate then blocks on its own files. The file is created when absent, appended to when present (your own lines are preserved), and a second run reports it as already ignored instead of appending again. The same run prints the `undo:` line for it.
- `init`'s `undo:` line is complete and truthful. It names every path the run created (`rm -rf`) and every file the run changed in place (`git restore --`: an appended `.gitlab-ci.yml` include, an appended `.pre-commit-config.yaml` entry, an added ignore rule), so following it can never delete pre-existing config, baselines, waivers, hooks or CI files. A run that changed nothing prints no undo line at all.
- `init` reports only what THAT run did. It keeps an existing `.gateforge.yml` and says so instead of first claiming to write a preset and then reporting it as untouched; the CI and provider lines name the server that actually exists (a GitLab-only repository is no longer told to configure GitHub branch protection), and a preset that wires no local hook says whether your existing commit hook and/or CI job still decides what blocks your commits. The doctor reads a framework-managed pre-commit hook the same way `init` does, so the two no longer contradict each other.
- `init` quotes evidence from application code. Hidden dot-folders (agent tooling, tool caches, leftover working directories) are not scanned, and a file inside an `archive/`, `vendor/`, `generated/`, `fixtures/`-style directory is quoted only when no application file carries the same signal. The generated `.gateforge.yml` carries the matching default excludes, so the detectors make the same choice.
- `init` asks ONE plane question per ROUTE FOLDER. It used to propose planes for MODEL directories only, so on a repository with many endpoints every discovered endpoint stayed `PLANE_UNRESOLVED` and every endpoint obligation and adapter waited on hand-edited JSON. A non-interactive run still proposes nothing and writes nothing for routes: it names each folder and prints the exact `gateforge classify plane` command. A linked model's plane may appear in the question as a HINT and is never applied — an `accounts` route can serve master data — and the hint is withheld whenever it would be a guess (an unresolved linked model, or two models that disagree).
- `gateforge classify plane` accepts a FOLDER or glob, not only one file, with the same owner review (`--reason`, `--confirm`). Route files arrive in folders; the per-file-only command meant hand-editing `planes.json`.
- Whole-folder documentation exclusion accepts data files. `--docs-exclude docs` used to be refused because the folder held `.json`, `.yaml`, `.csv` and `.html` files. An owner-declared documentation folder may now hold those five formats beside Markdown, reStructuredText, plain text, PDF and static raster images. Refusal is still by NAME first: `package.json`, `tsconfig.json`, `.pre-commit-config.yaml`, `.gitlab-ci.yml`, `pnpm-workspace.yaml`, `composer.json`, any `*.config.*` file and lockfiles stay refused inside an excluded folder, and MDX, WASM, SVG and unknown formats fail closed. HTML is accepted only as content of a declared folder; elsewhere it keeps full evidence identity. The format allowlist does not prove that an allowed file cannot affect behavior — the owner assertion and its reduced guarantee still apply, and the receipt/report already name the excluded folders.
- `--docs-exclude-file <path>` is the same assertion in a second spelling (one folder per line; blank lines and `#` comments ignored). Both spellings combine into one deduplicated list, and the interactive prompt now says the flag exists, so a long list does not have to be typed into one prompt.
- `init --behavior` works. `behavior` / `--no-behavior` were missing from the boolean-flag table, so `--behavior` demanded a value and swallowed the next argument. Both are registered as boolean flags now.
- `next` orders the work by business weight, so the first item is no longer a throwaway demo route. Routes linked to models and routes the frontend consumes rank first; every weight is additive and printed as a `why:` line, so the order explains itself.

### Endpoints & frontend calls

- Constant and annotated FastAPI prefixes are folded. `router: APIRouter = APIRouter(prefix="/api/v1")` is indexed exactly like the unannotated form (it used to be ignored, and every route behind it was published at the router's own prefix with no typed outcome), and a prefix that is a module-level string constant — on the router or on `include_router` — is provable from the source, so the route keeps its real path. An f-string, an attribute or a call is genuinely computed: the router yields `FASTAPI_PREFIX_UNRESOLVED` and no route is emitted, which is the honest answer rather than a prefix-less path no app serves.
- `FASTAPI_ROUTER_UNMOUNTED` is a new blocking code. A router that no scanned `include_router` targets is served by no scanned app; its routes keep their standalone emission and one typed entry names the router, its file and every declared route, so "the prefix was not applied" is never the answer when the real one is "nothing mounts this router". It is reported only when the scanned set shows an application and has no unresolvable include.
- A router built by an unmodeled expression (`router = build_router()`, a subscript, an attribute) reports `FASTAPI_PREFIX_UNRESOLVED` naming the variable, never as prefix-less paths.
- `HTTP_METHOD_DYNAMIC` is a new blocking code, and the method of a `fetch(url, options)` call is read from a bounded request-options model instead of defaulting to `GET` when the options were not inline. An inline object resolves with last-writer-wins (a spread and the override after it both participate), a module-scope constant is read; a method that cannot be resolved is `HTTP_METHOD_DYNAMIC`, never a fabricated `GET`. This removes false `FRONTEND_ROUTE_UNWIRED` findings where the real route existed under another verb.
- An `api.<verb>()` call counts as a route registration only in a file that imports a server framework (express/fastify/hono). That is also how an axios instance, a Playwright request context or an api-client module spells its calls, and reading those as routes minted server routes out of test and client call sites.
- An endpoint's location is its SERVER ROUTE, not a frontend call site that happens to mention the path.
- `ENDPOINT_RESOURCE_CANDIDATE_UNMATCHED` is a new code. A by-id route whose path-derived resource name names NO discovered business resource used to be silent, which made a real route look absent from the inventory (`GET /api/v1/reports/logs/{}`, served by a table named `report_logs`). The entry names the endpoint, the derived name, and up to three near matches among the discovered resources (a discovered name whose last `_`-segment equals the candidate or its singular/plural variant), sorted. They are CANDIDATES for the owner and are never linked: linkage still requires an exact name match plus a schema-symbol or handler-name corroboration fact. A route that links, or one with nothing near it (the entry then carries no match list), is unaffected — as is a collection route, where no adapter read is at stake.
- **The owner decides whether unmatched by-id routes block.** `endpoints.unmatchedRoutes: block | warn` in `.gateforge.yml` grades the entry above. ABSENT — an existing repository that upgraded — keeps them **advisory**: they stay in the report under the same code, `check --changed` does not block on them, and `check` and `next` print a banner at the TOP naming the count, the first three examples with their near matches, and the exact key that turns blocking on. `warn` is the same once the owner has said so, without the "you have not chosen" sentence. `block` is today's strict behavior. On a large existing repository the strict default added 89 blocking entries and blocked every commit, so the honest default for a repository that never chose is to report loudly and block nothing. `gateforge init` asks the question once in a terminal, writes `warn` plus the exact setting on a headless run, and takes `--unmatched-routes block|warn`.

### Resource graph & planes

- Models declared in test directories no longer enter the resource graph. A pytest module that re-declares a table on its own `Base` to build rows (next to the application's real model) used to enter as a second business resource; the real table then collided with its own fixture, stayed plane-unresolved, and blocked with no honest answer. Files under a `test/` or `tests/` directory segment are still parsed and still reported in `scannedPaths` — the coverage evidence stays honest — but they contribute no resource, unresolved entry, signal or duplicate finding. This is the same rule `init` already applied when it refused to infer a business plane for a fixture table, now applied to the graph.
- The per-tenant singleton tag is minted only on an EXACT configured scope. `singletonPerTenant` was tagged when ANY unique constraint merely CONTAINED a tenant-scope column, so a table whose `tenant_id` means something else in its own domain was reported as "exactly one row per tenant exists" and its create as provable only on a fresh tenant — false, and blocking on a claim that was never true. A table is tagged only when its plane evidence is `tenant` AND one declared UNIQUE constraint or UNIQUE INDEX is written over tenancy-scope columns and nothing else. The declarative `tenancy.scopeColumns` list still replaces the default column list, so a repository whose scope column is not one of the defaults is recognized.
- Route-folder plane proposals scan exactly what the pipeline scans (the gitignore rule above applies to them too): a route file inside a gitignored untracked folder produces no proposal, because no folder the owner could act on hides in generated output.

### Adapter scaffold

- The scaffold names the route that exists and the real blocker. `adapters scaffold` reported "no GET route serves one accounts entity" for routes that discover had already linked, because the route view skipped every plane-unresolved endpoint; the refusal now names the existing route and what is missing ("its plane is unanswered — answer the plane first"), and names routes blocked by an unanswered plane instead of staying silent.
- List-only adapters are generated. The kit has always accepted `listPath` alone and resolves the member from the collection, but the scaffold refused every resource without a by-id route; a resource with a complete collection and no by-id route now gets a list-only adapter (list path, collection key, paging) and the header says so.
- Guesses are not written. A route reached only by NAME matching is never taken as a by-id read, and a route with a literal segment between the resource segment and `{id}` is never taken as a by-id read — that shape is a lookup by some other key, and a wrong read path produces an adapter that fails closed against the real server. Each becomes a "needs you" entry with its reason instead.
- A scaffolded path taken from a router no app mounts is marked in the file's own header and the owner is asked to confirm it.

### Test catalog & suggestions

- `tests suggest` is RANKED and CAPPED. Candidates used to be listed alphabetically by file — hundreds per obligation, the obvious test buried at #159 of 311 even when its title carried the obligation's own `@crud(...)` tag. Candidates are now scored by the evidence the catalog row carries (explicit tag, resource token in title or file, the obligation's operation word, a route segment from the run's route inventory, an unmocked `real/` folder, minus a mock signal), every weight is printed as a `why:` line, ties break on the logical key, and the text surface prints the top five and says how many it hid. `--json` carries every candidate with its `rank` and `score`.
- `tests suggest --json` narrows `candidates[].overlaps` — a **non-additive** JSON change. The field listed every obligation that merely had the test among its CANDIDATES; on a real repository that was 237,936 entries for a handful of suggestions. It now lists only the obligations that DECLARE the test (native declaration or the `test-map.yml` sidecar), which is what an overlap means. Consumers reading `candidates[].overlaps` must be re-checked: the field is narrower, not merely re-ordered.
- One instruction, not two. When an existing test fits, the next action is to mark THAT test `observed-e2e` and run it under the witness; the overlay instruction ("write a new test in `tests/e2e/gateforge/`") belongs to `newTestNeeded: true`. A suggestion block no longer tells you to write a new overlay test and, in the same breath, to reuse the test it just listed.
- `already declared for: …` is printed only when a declaration exists (a `test-map.yml` entry or an `@gateforge` annotation). An inferred or prior-run binding is a suggestion, never a declaration.
- `check` shows declared-but-unwitnessed mappings: `mapped to: <test keys> (not yet witnessed)` for every obligation whose test ids are declared but whose records were not consulted. In the TEXT report the next action names the command that collects the evidence instead of the generic "write a test" advice; `--format json` keeps the cause's own generic next action and instead carries `declaredTests` and `mappingState: "declared" | "declared-not-witnessed"`. Only DECLARED ids appear there.
- Tests are attributed to the runner that owns them. The static scan is seeded from Gateforge's include globs, so test-shaped calls anywhere in the repository became catalog rows; each runner's OWN file selection is now read as data and decides the row's runner — Playwright from the enumeration's project-graph reporter (`testDir`, `testMatch`, `testIgnore`), Vitest from `vitest.config.*`/`vite.config.*` read with the TypeScript AST only. With `globals: true`, a bare `describe`/`it` is a registration the runner owns, not an alias gap. Every selection is FAIL-OPEN and says so (an unreadable pattern selects everything, as before, and the summary line states which selection could not be read); a file no runner claims keeps the configured runner and stays a blocking row — ownership is never invented.
- Stale roadmap text is gone from shipped output ("execution and evidence sealing land in Phase 4" shipped long ago), and a declaration is reported as "declared in test-map.yml" without guessing who made it.

### Release hygiene

- No Python bytecode in a published tarball. 0.8.0 reached npm carrying `__pycache__/*.pyc` in four packages because a manual `npm publish` ran from a tree whose detectors had executed. Every manifest that ships a `python` directory now ends its `files` list with `!**/__pycache__`, `!**/*.pyc` and `!**/*.pyo`, and `scripts/release-publish.sh` refuses the WHOLE release — before publishing anything — when `npm pack --dry-run --json --workspaces` still names one, printing the package and the path. Publish from the tag workflow (`v0.9.0`) or from the verified `.tgz` files (`npm run pack:check` prints the lists).
- The test suite no longer reads the developer's verifier keyring: keys are isolated per run, so a local suite result does not depend on the machine it ran on.

### Fixed

- A `persistence:read` whose observe binding declares `collection` no longer stops proving once the list outgrows 16 KB. The witness parsed the first 16,384 bytes of the response it proxied, so a bigger list named no complete row and the claim stayed `EVIDENCE_NOT_COLLECTED` with no receipt sealed — a failure that grew every run as the app's own data grew (in the session that motivated this release, a users list at 18,526 bytes over 107 rows took acceptance from 70/70 to 69/70, and the same list had been under the cap one release earlier). Such a read is now parsed from its OWN bounded copy — up to 1 MiB and up to 10,000 rows — so a real app's normal data size can no longer make a passing test unprovable. Nothing else moved: the 16 KB response tap is byte-identical, so the body digest and the create-attribution log read exactly what they always did; only the declared `idKey` is read, exactly as before; and the record payload is unchanged, so every record and receipt already sealed re-verifies. A body or a page past the new bounds is refused, never partially read, with a note naming the bound and the measured size.

### Upgrading from 0.7.x

No configuration change is needed and every new option is off by default, except that `test-gates` under `CI=true` now prints a progress stream on stderr (`run.progress: off` restores the 0.7 output). Run one new witnessed run after upgrading: a receipt sealed by 0.7.x is refused with `EVIDENCE_STALE` because the new engine derives the gate inputs again; `gateforge test-gates --changed` re-seals it, and the owner-approved policy digest stays the same. Steps, behavior changes and the option table: `packages/cli/guides/UPGRADE-0.7-to-0.8.md`. If `package.json` also pins `@gate-forge/*` in `overrides`/`resolutions` or through an `npm:@gate-forge/…` alias, set those entries to `0.8.0` by hand before installing; otherwise npm stops with `EOVERRIDE` (see the guide).

Passing local runs keep their previous output. A failed local run with progress off now reports up to three failed tests and their first error line. On Linux, the doctor and run preflight also probe installed Chromium-family executables; a missing system library is a runner failure with an `install-deps` command, not a successful readiness check.

### Added
- A Playwright run whose planned projects are named now executes against ONE globally prepared candidate. A `setup` project's saved session used to exist only in the working tree, so the candidate was frozen before native setup and a run then correctly refused to seal when genuine setup changed the counted session-state bytes, even if every test passed; declared native dependencies already ordered each setup ahead of its own dependent body, so what was missing was anywhere to admit genuine generated output, and a guarantee that no INDEPENDENT body starts before ALL preparation. The prerequisite closure now runs first — each stage genuinely executed, with its own outcome retained as a witnessed prerequisite — the candidate is taken once in between (the generated controller is a dependency of every body project, so the runner's own topological scheduler orders it), and every body executes against those frozen bytes. No body starts until a SIGNED release opens the barrier: the Ed25519 private key exists only in the CLI process's memory and is never written to disk, the controller receives the public key and verifies the release against the run, the invocation, the nonce, the prepared tree and the sha256 of its own spec bytes, and a refusal document is failure-only (it can end the controller's wait sooner, never admit a body). Between the pre-run baseline and the prepared candidate, only an untracked, non-input, non-excluded, physically contained regular file that a project declares as its `storageState` may differ — additions and modifications only, never a removal, a symlink or any other change to a candidate file — while source, trusted policy and the input digest stay frozen for the run; the engine's own run artifacts are written to the excluded run-state directory and are not candidate files. Unnamed or empty projects take no part, a non-Playwright runner never enters this path, and an operator-set whole-run session state bypasses it exactly as before. The controller is generated as plain ESM JavaScript under a `.mjs` name, so its module kind comes from the file itself and a repository whose root `package.json` is CommonJS, declares `"type": "module"`, or nests its specs in their own module package runs the same freeze unchanged; before this a CommonJS root had the controller `require`d, which turned its ESM imports into `require()` of a `file:` URL and failed the run with zero outcomes. A project's environment keeps the runner's original semantics: a dependency's produced environment is still unioned into its dependents, and the controller projects the trusted baseline back inside its own worker, so a prerequisite's assignment reaches exactly the projects that depend on it. `check --require-e2e` and the broker grade the same candidate the run sealed. This is a checked, signed boundary inside the run, not a sandbox — ordinary local files are not OS-immutable and stay writable by your own user.
- `enforcement.reseal` now derives the READERS of a changed session state. A path a project declares as its `use.storageState` is classified from the sealed runner config's own bytes: when it changes and is eligible generated output (untracked in both sealed commits, outside the run's input snapshot, an ordinary file in the candidate, not a removal), the re-seal demands every test that reads it — the declaring project's tests, the projects ordered after it, closed over file importers — and a changed state this run can name no consumer for is refused rather than carried. The path stays in the signed `changedPaths`; it never becomes a disregarded runtime file and never invents a receipt key. The precedence is the point: an `enforcement.resealRuntimeFiles` glob is a claim about bytes, while a sealed `storageState` declaration is a claim about who READS them, so a glob can no longer swallow a nominated state (an input-bound one now refuses instead of passing), and when the sealed declarations cannot be computed at all no raw non-test path may be disregarded, because that refusal is the only thing that reports the doubt. A path the sealed config never names is still disregarded exactly as before, which is what an ordinary runner cache relies on.
- The existing runtime document's `envAllowlist` now supplies explicitly named operator values to supervised tests and wired enumeration. Native helpers can use their service URLs without inheriting the whole environment. Engine wiring and process-loader controls are refused; absent lists forward nothing new. A supervised `test-gates` run refuses such a reserved control with a usage error before the harness, the pipeline, or native test enumeration starts, so the refusal lands ahead of any candidate-controlled configuration; every other allowlisted name is granted exactly as before.
- Optional COLLECTION read binding for a suite-driven browser test whose UI reads a LIST. The observe read binding now takes `{method: 'GET', path, collection: {rowsKey?, idKey}}` (omit `rowsKey` when the response root is the row array): the witness parses only the declared `idKey` out of only the declared rows of only the 2xx response it proxied itself, resolves the returned ids against the adapter snapshot it took when the session opened, and reads one of them through the adapter exactly as a by-id read is graded. Without it a read binds `{id}` from the path exactly as before, and a collection may only be declared on a read + `GET` whose path carries no `{id}` — every other shape is refused when the adapter loads, never inferred from a response body. A selector is a logical key or a unique substring of one, resolved against the planned rows (never raw runner output); an unknown or ambiguous selector exits 2 with the candidate keys listed. The named run uses the additive `named-selection` selection mode, so it can never collide with a full or scoped seal, and adds `selectors: [{ selector, logicalKeys }]` to the report. It works for every runner through the shared adapter contract.
- Opt-in `enforcement.reseal: true` lets `test-gates --changed --scope changed` re-seal after a test-only change: Gateforge diffs the two sealed trees itself, classifies every changed path from the runner's catalog and the repository import graph, re-runs only the tests the change can affect (importers of a changed file included) and carries the parent's outcomes. Eligible paths are test files and test helpers only; app code, a deleted file, a setup or dependency-stage test, or an unresolvable import falls back to the plain changed-scope run with one plain reason line. A complete whole-suite run that failed a test seals no receipt and leaves `.gateforge/test-gates/run-record.json` instead — a MAC'd, verdict-free run record the same path re-seals from when every test that did not pass is inside the affected set and passes now. The chain is bounded at 5 consecutive re-seals, and `check --require-e2e` and `broker commit` recompute every hop (parent authentication, tree diff, classification, affected set, carried rest) with their own keyring. Off by default in every mode; `enforcement.reseal: true` enables it in any mode, `strict` included. When the path is on and the run state holds a parent document it cannot re-seal from, the run says so in one plain line naming the first binding that failed — `test-gates: the previous run cannot be re-sealed from: its sealed tree is not the tree of commit 9c8a3b7 (uncommitted changes were tested) → changed-scope run` — instead of silently taking the changed-scope path. The parent is bound to the commit the parent DOCUMENT names, which must exist in the checkout and be an ancestor of HEAD — no CI variable is involved, and `CI_MERGE_REQUEST_DIFF_BASE_SHA`/`GITHUB_BASE_REF` are ignored, so a CI run must persist `.gateforge/test-gates/` between pipelines (a cache keyed by branch); with a cold cache there is no parent and the run is the ordinary run. With the path off, or with no parent document at all, the output is unchanged byte for byte.
- `enforcement.resealRuntimeFiles` lets the owner declare the runtime state the run itself rewrites inside the repository (a witnessed login stage's storage state, a runner cache) as repo-root-relative globs, so a re-seal is not blocked forever by gitignored bytes that differ between every pair of sealed candidate trees. A matching changed path is disregarded only when **neither** sealed commit tracks it — a committed path is source, whatever the glob reads, so a declaration can never hide a source change. The run prints one plain line (`test-gates: re-seal disregards 2 declared runtime file(s): …`), the re-sealed receipt keeps the real `changedPaths` and adds `resealDisregarded`, and `check --require-e2e` and the broker recompute that exact list from the same globs or reject the receipt as `EVIDENCE_STALE`. Absent by default: a repository that declares nothing is byte-identical, and it refused with `app file changed: e2e/.auth/contractor.json → changed-scope run` until the key was added.
- A dynamic import with a **literal** specifier is now an ordinary import edge instead of a refusal: `import('./x.mjs')`, `import("./x.mjs")`, `` import(`./x.mjs`) ``, `require('./x')`, `importlib.import_module('x')` and `__import__('x')` resolve like a static import, so the file that loads the module re-runs with every importer of what it loads. A **computed** specifier — a variable, a concatenation, a template with `${…}` — still refuses the re-seal, and a call with anything but a single literal argument is treated as computed (fail closed). Before this, one tracked file with `import('./master_session.mjs')` refused EVERY re-seal in the repository with `unresolvable import: … computed specifier`.
- A re-seal now re-runs a runner project's DEPENDENCY stage when a test that depends on it changes. The standard auth pattern — a `setup` project owning `*.setup.ts` with the browser project depending on it — runs the setup tests before the dependent ones, so a change to one dependent spec re-executes the setup project too; the re-seal's affected set now names that stage, so the run's plan and the affected set `check --require-e2e` and the broker recompute agree. Before this, the run sealed a receipt and the very next `check` refused it with `re-sealed receipt re-ran tests outside the recomputed affected set (e2e/auth.setup.ts)` — the re-seal was unusable for every consumer using a setup project. Only files a declared `dependencies` project owns are added (resolved from that project's own `testMatch`); a setup-named file with no such edge is still carried, a CHANGED setup or dependency-stage test still refuses the re-seal with `setup test changed: …`, and an unresolvable dependency declaration still fails the change set closed.

- A secret-free CI progress stream (`gateforge test-gates --progress stderr|file:<path>|off`, and the additive `run.progress` config key). It prints the start line with the registered expected-set size, one line per finished test with exact `N/M` counters and the test's catalog title, an alive line every genuinely quiet minute, and the finish line before grading. It is built from witness-side facts only — counters, identities, catalog titles, outcomes — and NEVER from runner output, so it is secret-free by construction; a failing test's first error line is matched against credential shapes and replaced whole. `auto` is stderr under `CI=true` and off everywhere else, so a local run's bytes are unchanged, and the stream is written only when it is on. It decides nothing: it is not evidence, no gate reads it, and a write failure warns once and is then ignored.
- A failing witnessed test ships a Gateforge-owned diagnosis instead of a browser snapshot: `.gateforge/test-gates/failures.json` carries each failure's logical key, its guarded error message and up to five `file:line` stack frames. No request or response body is ever included, and a planted credential in an error message reaches neither the stream nor the artifact.
- `execution.repositoryDebt` gained `baselined`, `newlyBlocking` and `notGradedBlocking` beside the frozen `blocking` total (which stays exactly as computed: repository blocking verdicts + repository findings), and the text summary now reads `repository debt: N known (baselined), M new blocking / …`. All of them come from ONE definition over the graded verdicts, so the text and the JSON can never disagree, and `M` is exactly what this run's exit code blocks on: a full run's whole surface, a changed- or named-scope run's own slice. Debt outside a slice run is reported with its own words (`not graded by this changed-scope run: K blocking obligation(s) — …`), never counted as new.
- `gateforge test-gates --help` documents `--progress`, and the run's scope is published to the in-runner reporter as `run-scope.json` (derived run state, read by nothing the gate trusts).
- Candidate-tree ingestion hashes and stores its objects in process instead of spawning `git hash-object` per file and `git mktree` per directory level. The tree id for the same bytes is unchanged, every object is still an ordinary loose object in the same authority store (so `git diff-tree`/`git cat-file` on the candidate tree are unaffected), the same files are hashed (gitignored ones and `node_modules` included — a swapped package still voids the receipt), and every fail-closed rule and message is unchanged. Ingestion now costs two git processes in total, whatever the workspace size.

### Changed

- A named or changed-scope run's in-runner reporter no longer prints a repository verdict it cannot own: it says `GATEFORGE GATE: SELECTION (N satisfied, 0 blocking; repository verdict not graded here)` instead of `NOT PASSED` over debt the run never observed, which contradicted the CLI exit code printed seconds later. A selection whose own claim is unsatisfied still prints `FAIL`; a whole-repository run is unchanged.
- One run can no longer show two different repository-debt counts. The in-suite Playwright reporter graded claims only, so its `N known (baselined) / M new blocking` split was a guess beside the gate's: a real run printed `412 known (baselined), 87 new blocking` from the reporter and `396 known (baselined), 0 new blocking` from the CLI for the same 519 obligations, while the CLI's own JSON said `blocking: 96` beside `newlyBlocking: 0`. The reporter now prints `repository debt: graded by gateforge after the run` and `run-summary.json` carries only its legacy keys (`obligations`, `unclaimed`, `blocking`), and the gate's `newlyBlocking` is the count it blocks on instead of the total minus the baselined count. The `debt-baseline.json` run-state view is gone: a baseline id list is not the gate's grading, so nothing derived a split from it.
- A changed- or named-scope run no longer reports repository debt it does not block on as `new blocking`: a real run exited 0 on three selected tests while the repository carried 96 `missing` obligations, and the line would have said `96 new blocking`. `newlyBlocking` is now exactly the count the run's exit code blocks on, and the untouched debt is named in its own line (`not graded by this changed-scope run: 96 blocking obligation(s) — this run never observed them; a full run grades them`). A full-scope run's numbers, and the frozen `blocking` total of every run, are unchanged.
- `tests discover` never narrows several Playwright configs silently: when a repo holds more than one, the runner line now names every config it found, the one enumeration ran, why that one, and the ones NOT inventoried (their test cases are missing from the catalog). The chosen config, the invocation and every field are unchanged.
- `enforcement doctor` no longer calls a tarball install the registry: its `engine:` line now reads npm's own install metadata (the owning `node_modules/.package-lock.json`, else the manifest's `_resolved`/`_from`) and says `from node_modules (tarball or directory install: file:… — not the published registry release, so CI installing @gate-forge/cli@<version> would NOT run this code)`, or `… (registry or tarball install — no install metadata found, so the provenance is unproven)` when there is none. The receipt-bound `engine.source` keeps its meaning, so no receipt changes meaning and no receipt validity changes.
- Editing the repository's own `.pre-commit-config.yaml` is now announced as an action: `init --blocking`/`enforce` print one line naming the file as yours and the exact way back — `undo: git restore -- .pre-commit-config.yaml` for a tracked file, and (for an untracked one, which has nothing to restore) the line says to delete the appended entry instead of printing a command that would fail. The doctor's `hook-mutation` warning is now actionable in the order the owner meets it: it names those hooks as the repository's own and says to run `gateforge init --blocking` (or `enforce`) first, then move `gateforge-check` to the FIRST entry, instead of telling someone to reorder a hook they do not have yet. No file, exit code, or check id changes.
- The first real `next` on a FastAPI repository explains its owner question before asking it: one plain line says the route has no data plane, that no detector can read the answer from the code, and what each answer does (`tenant` / `master` / `global` → run only that `classify plane` command; a route no real user calls → the owner-only internal rule). The question itself, every printed command, the cause vocabulary and the exit code are unchanged; the `guidance` array gains that one line, before the question.
- Reports gained additive fields only, and only when they apply: `strictness` (non-strict modes) and `quarantine` (non-empty population). SARIF output stays machine-parseable JSON.
- `gateforge adapters scaffold` generates adapters that match a hand-written one far more often: a per-parent sub-collection (`/contracts/{contractId}/invoices`) is never sold as the complete collection (and never as a by-id read), route naming matches across `_`/`-` per whole path segment, `deletion` follows the graph's own soft-delete signal (a soft-delete-looking column raises a "needs you" line instead of a silent hard delete), and `fields` projects every column the graph declares for the table — the SQLAlchemy detector now reports `columnNames` — minus the primary key and credential-shaped columns, which the file header names.
- The adapter scaffold never projects a primary key as a business field, whichever layer declared it (the classification or the table's own `primaryKeyColumns`), and its header omits the `excluded:` clause when nothing was excluded.

On the canonical FastAPI full-stack template it ended the whole `gateforge next` loop with `do: gateforge discover --json` — a read-only dump, so the documented agent loop printed the identical block forever, and (unlike `ENDPOINT_SEMANTICS_UNRESOLVED`) the cause carried no guidance at all. `next` now prints why it blocks (the mount's prefix is an expression, so no route under it can be read statically, and a guessed path would describe routes the app does not serve) and the one fix that closes it: write the prefix as a literal string at the mount site the finding names (`app.include_router(router, prefix="/api/v1")`) and run `next` again. Nothing that does not work for this finding is printed — a `.gateforge/endpoints.json` capability rule has no detected route to select on, `gateforge waive` has no obligation to bind (`waive: no obligation resolves for …`, exit 2), and `.gateforge/fastapi.json`'s `importRoots` governs absolute imports, not a computed prefix (all three verified against the real in-process pack, and the literal fix pinned by the pack's own real-detector test). A declaration key for computed prefixes is NOT introduced here; it is reported to the pack owner as a proposal. `--json` gains the additive `fastapiPrefixGuidance` array and keeps every existing key; a repository without this finding prints nothing new.
- `gateforge key create --confirm` on an existing key ring now says what is already there instead of a bare "refusing to overwrite". The quickstart step runs on a machine that may already hold a ring (a second project, a re-run of the guide), and the refusal named neither the active key nor the way forward, while the very next command (`enforcement doctor`) reported that same key as active and resolving — so a correct machine contradicted the documented expectation and a user read "refusing" as a failure. The message now names the ring's path, its active key ID (never the secret), that nothing needs doing while that key is active, and `gateforge key rotate --confirm` as the command for a new key. The exit code is unchanged, and a file that is not a readable key ring keeps the plain refusal — naming a rotation for an unknown file would be advice nobody could follow.
- An `ENDPOINT_SEMANTICS_UNRESOLVED` block is now answerable from the output alone. It used to end in `do: gateforge discover --json` — a read-only dump that changes nothing, so the documented agent loop (run the printed command, run `next` again) repeated the identical block forever on any repository whose handlers delegate to a service layer. `gateforge next` now prints the owner-authored `.gateforge/endpoints.json` rule for THAT endpoint (its own method and canonical path as the selectors, the two owner-chosen fields marked, their allowed values named — `crud-archive`/`crud-delete` on a DELETE, the closed compiler vocabulary otherwise), plus the `gateforge explain` command that proves the declaration applied. The snippet is the product's own schema, so a rule filled in from it parses and resolves the block; a rule left with a placeholder capability still fails closed at startup (exit 2) with the allowed values. `--json` gains the additive `endpointSemanticsGuidance` array and keeps its existing fields, and a repository with no unresolved endpoint prints nothing new.
- The documented verifier-key ceremony now creates the key ring the product actually reads. `QUICKSTART` step 6 (and the same block in `TEST-ENVIRONMENT.md` and `UPGRADE-0.6-to-0.7.md`) told a user to create `$HOME/.config/gateforge/keys.json` and export `GATEFORGE_WITNESS_VERIFIER_KEY_FILE` for it, while `gateforge key create` with no `--file` writes `${XDG_CONFIG_HOME:-$HOME/.config}/gateforge/verifier-keyring.json` and every later command — including `enforcement doctor`'s `verifier-key` check — reads that path. On any machine with a non-default `XDG_CONFIG_HOME` (most CI images) the documented command therefore produced a ring nothing read, and a second `key create` was needed that no guide mentioned. All three guides now run `gateforge key create --confirm` alone, say which file that creates, and say that `--file` is for a ring that really lives elsewhere (with the matching export). The CLI README names the same default path.
- The example app's "Gateforge first run" now says how to install Gateforge. A tarball or directory install lands in `node_modules` exactly like a registry release, so the doctor was fixed to name the truth while the reports kept claiming `engine: 0.7.1 from registry` for the very same repository — and the false claim is the one a consumer's CI reads. A full-scope run opened with `scope: full (62 mapped tests)` in a repository that has no test map at all and no obligation to mark — the number is the discovered CATALOG the run plans to execute, not a count of declarations, so the one number a user reads to check whether their `tests mark` took effect told them they had mapped 62 tests when they had mapped none. The line reads `planned tests` (the same word the runner's own selector diagnostics already use); its shape, the `--scope changed` advice and the rest of the line are unchanged.

The exit code is unchanged, and `CONNECT-YOUR-PROJECT.md` now shows one complete, correct `plugins:` entry with the rule.
- `gateforge init` now recognises a SQLModel table whose base is declared through another class, so the canonical FastAPI template stops being read as a repository with no data layer. The scan's needle required `SQLModel` written literally in the class head, so `class UserBase(SQLModel)` + `class User(UserBase, table=True)` — the layout the template itself ships — produced no `sqlalchemy` signal at all: `init` recommended `pack-fastapi, pack-http` and never `pack-sqlalchemy`, the one pack whose proof channel that persistence layer needs, and the run it wrote had nothing to grade a model against. The scan now resolves the base chain: a `table=True` class whose base reaches SQLModel through classes the same module declares, or through a name imported from a module that declares a SQLModel class, is a model, and the printed reason quotes the class head it found (`class User(UserBase, table=True)` in `backend/app/models.py`). A chain that never reaches SQLModel is never promoted.
- `enforcement doctor` and the run preflight no longer call a browser cache ready when the browser builds the run would launch are not in it. A supervised run launches the CONSUMER's Playwright — the package that resolves next to its own config, usually a different release from the hoisted one — and each release pins its own browser revisions in the `browsers.json` of the package it launches. Both surfaces only counted cache ENTRIES, so on a machine where another project had already installed a different Playwright they reported `[OK] runner: playwright installed; browsers installed (N entries)` and the first witnessed run then failed EVERY test with `Executable doesn't exist at .../chromium_headless_shell-<revision>/…`. The `runner` line of both surfaces now resolves the runner exactly as the run does (`@playwright/test` first), reads its own registry, and checks the builds the config's projects would launch (each named `browserName`, chromium plus its headless shell by default, skipped when the config turns headless off). A missing build is a `fail` naming the exact `npx playwright install <browsers>` and the directory that must run it (the one holding the config, so a sub-project's own install is fixed in place); all builds present keeps the historical wording plus the verified build names; a runner that ships no readable registry keeps its exact previous line. `TEST-ENVIRONMENT.md` gains the matching checklist rule.
- The response-field advisory no longer accuses the two shapes that are not model reads (after a run on a real FastAPI + React app produced only false positives). (1) Error-envelope reads: a branch that opens on the call's own envelope is read for its POLARITY and only its failure arm is dropped, because the body a failure branch reads (`res.data?.detail`) is the server's error envelope, never the success model. `if (res.ok)`, `if (res.ok === true)`, `if (res.status >= 400)`, `> 399`, `!== 200`, `!== 201`, `< 400`, `=== 200`, `<= 299` and their negations decide which arm runs, so the SUCCESS arm keeps its reads — `if (res.ok) setItems(res.data.items)` is the most common success path and is exactly where a dropped field hides — and a read after an early-return guard is still reported when the success model dropped the field. A compound condition (`!res.ok || res.status >= 500`), a comparison the pass cannot read (`>= Math.min(400, limit)`) and a `statusText` test are undecidable, so both arms are dropped. A ternary is the same guard as an `if` (`res.ok ? res.data.items : res.data?.detail` keeps the success arm); a ternary on anything else is not a guard, so both of its arms are ordinary reads. Independently, `@gate-forge/pack-fastapi` now always declares `detail` among a route's wire names, because FastAPI's own error body is `{"detail": …}`, so even a stray `detail` read outside a guard is never flagged. (2) Fallback chains: a read that is one operand of a `||` / `??` chain now carries that chain's index, and the check judges the chain as the ONE decision it is — `res.data?.invoice_id || res.data?.invoice?.id` is silent when the model declares `invoice_id`, because `invoice` is its defensive fallback; a chain in which no operand is declared is still reported whole. Nothing about the advisory's blocking behavior, its exit code or the byte-identity of a repository with no gap changed.
- A run can no longer be sealed against a witness that perturbs its timing, and a witness too old for run options can no longer pass for one that honored them. A NORMAL run against an external witness that was itself started with `GATEFORGE_CHAOS_SEED` was silently accepted, so a perturbed run could produce a receipt nobody could replay; it is now refused before any test runs (exit 2, one line naming the variable to unset). A witness that does not echo the options it was given is refused for `--chaos` (it would apply no schedule while reporting as if it had) and prints one plain line for twin coverage (it recorded no shapes while reporting twins that agreed). A normal run against a witness with no chaos plan — including one too old to have the schedule route, which answers 404 — is byte-identical to before: no chaos label, no extra output, the same exit code.
- A test-only re-seal now survives the runs a pipeline does in between. The parent's evidence was read out of the LIVE run state when the re-seal decided, so the first thing that rewrote `manifest.json` — a consumer's materialization pre-step, which drops the witness attestation envelope while leaving `receipt.json`, `run-record.json`, `records.json` and `claims.json` in place — took the envelope away and the re-seal refused with `its evidence carries no witness attestation envelope → changed-scope run`, exactly where the path matters most. The run that seals a receipt or writes a run record now retains its own records, claims and witness envelope in `.gateforge/test-gates/reseal-parent/`, atomically, replaced by the next run that seals a document there and cleared with the document it belongs to; the re-seal authenticates that copy (run id, input digest, `evidenceAttestationDigest` and the MAC under the consumer's keyring) and never falls back to the live documents, so a missing or tampered copy refuses with the same plain line. The copy is written only with `enforcement.reseal: true`, so a repository without the opt-in is byte-identical; no released key, code, exit code or receipt field changed.

- `gateforge run -- --changed --scope changed` no longer fails its own final step. The run sealed a receipt for the changed slice, then closed with a whole-repository `check --require-e2e`, which demanded evidence for every obligation the slice never meant to cover. A scoped run is now checked at the scope it sealed (`check --changed --require-e2e`, and the step line says so); every other run is checked whole, as before.
- `gateforge run -- … --witness-url <url>` no longer breaks its own run in the preflight. With an external witness the target base URL is that witness's observation proxy, which counts every exchange and refuses the run-context binding once it has seen one; the preflight's reachability probe went through it, so `test-gates` then failed with `refused run-context binding (HTTP 409)`. With `--witness-url` the target line now reads `not probed` (the witness attests the target itself); every other run probes exactly as before.
- `gateforge run` no longer refuses a repository whose Playwright is installed next to its config in a sub-directory (an `e2e/` project with its own `node_modules`, nothing at the root). The strict preflight looked only from the repository root upward, so it failed `runner: playwright is not installed` on a project whose supervised runs worked, and `gateforge run` stopped before the suite. The preflight and the doctor's Playwright line now resolve the runner where the supervised run does: next to the Playwright config first (`@playwright/test` before `playwright`), then from the root. A repository with a root install reads exactly as before.
- `example/workflow/server.js` now answers every request. A path it does not route used to fall out of the handler with the connection still open, so any liveness probe hung instead of getting an answer — and the witness's startup attestation (`GET /` must present the environment fingerprint) timed out and failed the whole run with `adapter target presents no 'x-gateforge-env-fingerprint' marker`. Unrouted requests are now `404 {"error":"not found"}`, like the `example/auth` and `example/webhook` servers already were. Every routed path, status and body is unchanged.
- A test-only re-seal now carries the parent's WITNESS EVIDENCE, not only its outcomes: the parent run's records and claims are retained (bound to the parent run's attestation, authenticated with the run's own keyring) and graded as the union with the re-run's own evidence, so an obligation only a carried test proved stays `satisfied` and `check --changed --require-e2e` exits 0 after the re-seal. Attribution is by the witness-issued test id, so a re-run test's parent record never survives; the receipt binds the union in the additive `carriedEvidenceDigest`, and `check --require-e2e` and the broker recompute the union from the retained documents and fail closed (`EVIDENCE_STALE`) when the state evidence is anything else. Before this, every re-sealed run graded what only a carried test had proved as `missing` and the next check failed on evidence the parent run had actually witnessed.
- Consecutive test-only re-seals now work end to end: a re-seal is itself a whole-suite proof (it names the parent it carried from and seals a `coveredObligationFingerprints` list covering the repository), so it can parent the next one. The run state retains the chain hop by hop in `.gateforge/test-gates/reseal-chain/` — each hop's parent receipt, that parent's execution result, the catalog the classification used, and the witness-issued records, claims and attestations of every contributing run — and a test no hop re-ran keeps its original proof. Three defects are fixed with it: the parent evidence was written over hop 1 and then shifted into hop 2 paired with the wrong document, so a second hop's envelope named a different run; a run that sealed no receipt left the chain behind, describing the parents of a receipt that was no longer there; and the carried count double-counted a test an inner hop had re-ran while the deeper runs' records were never authenticated, so the untouched spec graded `missing` on evidence three runs had witnessed. `check --require-e2e` and `broker commit` now walk the whole chain, authenticate every contributing run's envelope with their own keyring, and check the chain's carried total once against the receipt of record (`re-sealed receipt claims N carried test(s) but its chain holds M carried outcome(s)`). Before this, the second consecutive re-seal left `check --changed --require-e2e` failing on the untouched spec, or refused outright.

Everything else about declarative detection, the unresolved codes, and the exit codes is unchanged.

- Every re-seal refusal line now ends in what actually happens next: `→ changed-scope run`. The re-seal path is attempted only under `--scope changed`, so a refusal always falls through to the ordinary changed-scope run (a `scope: changed` receipt), never a full run. Before this, each refusal claimed `→ full run` while the run continued through the plain changed-scope path.
- The re-seal import scan no longer refuses on things that load nothing: a source file with non-ASCII text is read in full (object sizes are bytes, and the batch is now cut by bytes, not characters — before, the next file's header leaked into it and it "did not parse"), a local re-export `export { x };` is not an import, and a computed Python import only matters when a Python file changed (and a computed JS/TS import only when a non-Python file changed), because imports never cross that boundary. A real computed specifier in the changed file's language family still refuses, and a missing or truncated object in the batch now refuses instead of reading as an empty file.
- A static discovery row can no longer come from a file Git ignores. With the frontend of the FastAPI full-stack template built, `gateforge tests discover` planned 67 rows while Playwright enumerated 62: five came from `test(`-shaped methods inside the minified, git-IGNORED bundle in `backend/app/frontend/assets/`. The runner can never enumerate a test in a build output, so each of those rows sealed as a permanent `unenumeratedReason` gap and the run could not reach `inventoryComplete` even with every real test passing. Static candidates inside a Git work tree are now filtered through Git's own ignore rules in one batched query, so the same command plans 62 rows and reports `inventoryComplete=true`. A TRACKED file that matches an ignore pattern is still scanned and still fails closed as an unresolved row, and an untracked but NOT-ignored spec is still planned (a new spec must reach the plan before it is committed). Outside a work tree — plain fixture directories, or git unavailable — every candidate is kept exactly as before, and native `playwright --list` rows are untouched.

## 0.7.0

### Added

- Added existing-test discovery, suggestions, declarations, and the `gateforge tests surface-doctor` diagnostic.
- Added `gateforge key create|import-env|rotate|retire` for external verifier-key rings.
- Added `gateforge test-gates --changed --scope changed --result-only`; external-witness runs require a separate non-authoritative `--out` and never touch receipts.

### Changed

- `check` combines `.gateforge/test-map.yml` with optional `claimInventory` from a receipt authenticated for current inputs; `claims.json` alone does not declare claims.
- Docs exclusions use exact repo-relative folders via `gateforge init --docs-exclude`; a matching external `GATEFORGE_APPROVED_POLICY_DIGEST` is required, and recognized manifest/lockfile basenames remain protected.
- Trusted Playwright configuration maps `appBaseUrl` to `use.baseURL` and `storageState` to `use.storageState`.
- The Playwright package guard checks the supervised protocol contract and returns exit 2 with `GATEFORGE_PACKAGE_INCOMPATIBLE` on mismatch.
- `init --blocking` installs and verifies an active pre-commit hook and writes CI gate wiring.

### Fixed

- A linked raw/witnessed twin pair that ran but could not be compared is no longer silent. When one side sent no request through the witness — most often a raw twin written as a plain Playwright test, which opens no witness session — the run prints `test-gates: twin pair not compared: the raw test '…' sent no request through the witness` and how to make it observable (run the raw twin with the Gateforge test fixture), instead of reporting no divergence as if the twins agreed.
- A flag given three or more times keeps every value. `test-gates --test a --test b --test c` used to fuse the first values into one comma-joined selector (`'a,b'`), so naming three or more tests always failed with `TEST_SELECTOR_UNKNOWN`; the same applied to every other repeatable flag.
- Installing `@gate-forge/witness` no longer pulls in `bullmq` and `ioredis`, and loading it no longer needs them. The queue observer imported them at load time, so every witnessed run of a project without them (every project without a queue) died at start with `Cannot find package 'bullmq'`. They are now optional peers, loaded only when `.gateforge.yml` declares `queueObserver: { kind: bullmq }`; a project that declares it without them fails closed with the install command.
- The shipped `example/` project checks clean again with its new `webhook/` sub-project: that sub-project's engine-side modules (its evidence adapter, gate script and fixture provider) are excluded from the frontend call scan, like `behavior/`'s.
- The twin title convention now links the way pairs are usually written: `X [witnessed]: <what it proves>` next to `X raw: <what it does>`. Before, only an exact `X raw` (or a bare `X`) title linked, so a suite that labels both sides and then describes each one got no twin comparison at all and had to spell every pair out with `twinOf`. An exact `X raw` still wins; two described raw tests under one label link nothing (the owner names that pair with `twinOf`).
- A test-only re-seal now carries the evidence of natively claimed tests. Their records are stamped with the id the runner gave the test while it ran, which is not the enumerated catalog id when the trusted config lives in another directory, so the carry matched none of them: the re-sealed receipt said `carriedEvidence: true` while it carried no parent record, and `check --require-e2e` reported every carried test's obligations `missing` (it never passed wrongly). The execution result's outcomes now keep the runner's own id in the additive `runnerTestId`, and the carry uses it next to the logical key and the catalog id. A re-run test's parent records still never survive.
- Witness startup waits for the reported proxy URL before proceeding.
- Fixed a shared-distribution witness spool race between concurrent runs.
