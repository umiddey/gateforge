# Changelog

## Unreleased

### Added
- Run options travel with the run context, so a repository that starts its OWN witness gets timing chaos and twin path coverage with nothing configured on the witness side. Both features were only reachable through the spawn environment of a witness `test-gates` starts, so against `--witness-url` `--chaos` refused outright (`--chaos needs the witness this run spawns`) and an external witness answered `enabled: false` to the twin query — a comparison that silently compared nothing. The supervisor-authenticated `POST /run-context` now carries an additive, optional `options` object (`chaos: { seed, maxDelayMs, reorder }` and/or `twinShapes: { queryKeys, inventory }` — the inventory travels as its route TEMPLATES, never a path), the witness applies it for this run (its shared observation proxy reads the chaos plan lazily, so a plan bound after start-up still takes effect), and the binding answers with an additive `applied` echo. Absent `options` the request body and every byte of behavior are unchanged; a witness STARTED with the same feature keeps working exactly as before, and a binding that disagrees with how the witness was started is refused rather than silently resolved. `gateforge test-gates --chaos <seed> --result-only` is now accepted with `--witness-url`, and `enforcement.twinPaths` works against an external witness.

- Frontend-read / response-model gap advisory (plan 20260925-2011 Phase 4b item 5). `@gate-forge/pack-http` now reports `responseReads` on each frontend-call fact — the fields that call site reads off its own response (`.data.<field>`, `.data['<field>']`, destructuring of the awaited result or of its payload, followed by name inside the enclosing function, same file, never inferred across files; a `let` holder, a computed key and a JavaScript member are never reads) — and `@gate-forge/pack-fastapi` reports `responseModelFields` on each server-route fact: the wire names its response model answers to, field names plus declared aliases plus provably inherited fields, from the decorator's `response_model=` or else the handler's return annotation with FastAPI's own containers unwrapped. `gateforge check` cross-checks the two over the existing endpoint join and emits ONE non-blocking `RESPONSE_FIELD_MISSING_FROM_MODEL` advisory per field a joined endpoint's model does not declare, naming the endpoint, the field, the frontend file:line and the names the model does declare; a field counts as present under its own name, under the other case style (`due_date` ≡ `dueDate`), or under a declared alias. Nothing blocks and no exit code changes. A model the AST pass cannot compute (an alias generator, an unresolvable base, a `dict`, a union, no annotation), a call that resolves to no route, a repository without both packs and a malformed fact all produce nothing at all, so a report that has no gap is byte-identical to before.
- Per-session adapter identity (plan 20260925-2011 Phase 4b item 3b). A test that must read inside the tenant it just created registers that tenant's login for ITS OWN session: the new session-authenticated `POST /sessions/identity` (`sessionId`, `sessionToken`, `seat`, `values` keyed by the same witness env var names the adapter seat declares) stores the credential in witness MEMORY, keyed by that session id, and kit adapters resolve the seat by `ctx.sessionId` before the process-global witness environment seat (so a cookie logged in as one session is never served to another session's read). A registration changes only WHO the engine reads as — the engine still performs every read, a wrong tenant makes the row unfound (fail closed), a foreign or ended session is refused (403/409), and the credential reaches no record, no run state, no log and no report. Exposed as `evidence.registerSessionIdentity({seat, values})` on the frozen Playwright fixture surface and `WitnessClient.registerSessionIdentity(...)`; the trust argument is written out in `packages/cli/guides/TEST-ENVIRONMENT.md`. Without a registration every read is byte-identical to before.
- Per-tenant singleton facts and the obligation they hide (plan 20260925-2011 Phase 4b item 3a). `@gate-forge/pack-sqlalchemy` now reports every declared UNIQUE constraint, unique INDEX and column-level `unique=True` as the additive `uniqueConstraints` table attribute (absent when there is none; a computed column expression is never guessed), and tags a table `singletonPerTenant` (constraint, tenant column, columns) when its plane evidence says `tenant` AND one of those constraints includes a recognized tenant-scope column. `gateforge check` turns each tagged resource that owes a `persistence:create` into ONE non-blocking `RESOURCE_SINGLETON_PER_TENANT` advisory naming the constraint, the tenant column and the fact that the create can only be witnessed on a fresh tenant. Nothing blocks on it, and a repo without the tag is byte-identical. The matching per-session adapter identity lands with the same plan item: `POST /sessions/identity` registers a seat credential for one open session only, and kit adapters resolve it by `ctx.sessionId` before the process-global witness environment seat (credentials stay in witness memory — never in records, state, logs or reports).
- Owner-declared tenant scope columns (plan 20260925-2011 Phase 4b item 3a). `.gateforge.yml` gains an optional `tenancy.scopeColumns` list naming the columns that carry the tenant scope in THIS repository; `@gate-forge/pack-sqlalchemy` uses it INSTEAD of its fixed `TENANT_SCOPE_COLUMNS` list when minting `singletonPerTenant`, so a per-tenant singleton table scoped by `contractor_id` (unique `(contractor_id, ledger_id, kind)`) is recognized instead of silently missed. The declaration replaces rather than extends the default list, lives inside the trusted policy digest, and a malformed block fails closed. Absent (no file, no block, no list) is byte-identical to before, and the pack validates its own block only — an unrelated config problem still belongs to the CLI.
- Engine-owned queue observer (plan 20260925-2011 Phase 3): `.gateforge.yml` gains an optional `queueObserver` block (kind, connection, per-task-resource queue bindings, sampling interval, settle bound), parsed by ONE core schema the CLI and the witness both use. When it is configured the WITNESS opens the channel (built-in BullMQ implementation, or an operator module whose default export is a `(spec) => QueueChannel` factory), and an `engine-task` `deliver` case runs end to end: the engine produces the delivery (stamping the identity, the idempotency key and the attempt bound the case declares), polls the queue until every job settles, and seals that read as `queueObservation`. `attempts` rules now grade from it — terminal outcome, the declared attempt bound (with an optional `minAttempts` floor), and an optional `recoveredFromStall` claim proved by the engine's own timeline. Everything unexpected fails closed: an unknown backend state, an unbounded field, an over-long timeline or an undeclared queue blocks the case. WITHOUT the block the `task` namespace reports **unavailable** (every `task:*` contract fails closed with `VERIFIER_UNSUPPORTED`), the witness is handed no observer configuration at all (its spawn environment is byte-identical), and every `engine-task` case blocks with a naming diagnostic. Engine-level end-to-end suite (`packages/cli/test/task-queue-behavior-e2e.test.ts`, real CLI + real witness + real BullMQ app + real Redis, pass and fail variant per contract) and an example application under `example/task-bullmq/` that loses a worker process mid-job. The engine-owned observer is also what makes the `task` behavior pack OFFERABLE: `gateforge init` and `gateforge next` name it exactly like every other behavior pack (namespace, the file its needle was read from, and the `gateforge init --behavior-packs task` flag) ONLY when `.gateforge.yml` declares the block AND the repository shows the queue machinery or a discovered `task.resource`, because without the engine reading the queue every `task:*` case fails closed — a repository without an observer is byte-identical to one with no background work at all.
- Phase 4 setup UX: behavior cases are now installable by following what Gateforge prints. `gateforge init` reads the repository and names the behavior packs it finds (webhook / workflow / auth / validation — detected from the code that decides a signature, an authorization outcome, a state transition, or a request schema). A non-interactive run enables NOTHING and prints the exact `gateforge init --behavior-packs <pack>` for each pack it found; a terminal asks per pack. `--behavior-packs <pack,...>` enables the named packs, `--behavior` every detected one, `--no-behavior` keeps the run silent. The enabled packs' scaffold is written to `.gateforge/behavior.yml` as one commented example case each (a scaffold is never approval) and, for an existing `.gateforge.yml`, the exact `behaviorPolicy: .gateforge/behavior.yml` line to add is printed. An existing behavior document is never overwritten. `gateforge next` prints the whole remaining setup for a discovered route that has no approved case: the complete `endpoints:` entry (real resource id, method and path, the repository's own adapter-backed effect scope, its declared fixture recipe and the row a delivery records), the proof test that asks the ENGINE to drive each case, the `.gateforge/test-map.yml` entries with the exact compiled case ids, and the gate command. A fact the repository has not declared (no adapter-backed entity, no recipe, no declared created row) is printed as that fact, never as a block that could not pass. A repository that shows no behavior pack, and a `next` with no behavior obligation, are byte-identical to before. The `task` namespace joins those four under one gate: its example case is a `deliver` action on the `engine-task` channel with an `attempts` state rule, declared under `resources:` (a task resource is not a route), and the pack is offered only when a `queueObserver` makes those cases gradable. `gateforge next` prints the per-tenant singleton guidance (`singletonPerTenantGuidanceLines`, the same sentence `check` renders as an advisory) and, when it applies, the task-pack offer after the next action; both keys are omitted from `--json` and no line is printed for a repository with neither.
- `http.endpoint.requireObservation`, one additive option in the pinned policies document (`.gateforge/policies.yml`), makes an untested new route visible. Today a `consumed: true` endpoint policy owes `http:request-observed` / `http:response-status-ok` only for routes the frontend statically consumes, so a brand-new route no UI calls owes nothing and `check` exits 0. `options: { 'http.endpoint.requireObservation': all }` widens that one matcher to every discovered route: an unmapped one blocks with the existing `TEST_MAPPING_MISSING` cause and the existing overlay next action, naming the route. Existing routes are not re-litigated — `gateforge adopt` forgives them through the adopted baseline, so only NEW debt blocks. The option is absent-or-`consumed` by default and a document without it produces byte-identical output (locked by a golden report), it never widens a `consumed: false` policy, a policy that does not name the `http.endpoint` kind, or a table, it adds no contract, cause code or exit code, and it lives inside the trusted policy digest, so an agent cannot widen or narrow the scope by itself. `gateforge init` documents it in the policies template, and `gateforge next` names it on the one item it explains (an unmapped obligation on an unconsumed route) and nowhere else.
- `enforcement.twinPaths: advisory | block` (with `enforcement.twinQueryKeys`) makes a run say whether a raw test and its witnessed twin actually covered the same request path. The reported bug was GREEN: two tests shared a helper whose parameter defaults sent them down different paths (`?tab=all` in one, `?tab=open` in the other), so "green three times" proved nothing about the path the witnessed twin covered and nothing in the run said so. The witness proxy now records a request SHAPE per test session — a method, a route template and the values of the query keys the owner allowlists, never a URL, a body or a non-allowlisted value — and a run that finds a linked pair disagreeing reports `TWIN_PATH_DIVERGENT`, naming both tests and the exact differing value. The pair is linked by `twinOf` in `.gateforge/test-map.yml` or by the title convention (`X [witnessed]` next to `X raw`), and the raw twin's session is marked OBSERVATION-ONLY engine-side: every submission from it is refused with 403, so it can issue no record, no attestation and satisfy nothing. Additive and off by default — with `twinPaths` absent, or set with no pair linked, nothing is wired, no state file is written and the report is byte-identical. The comparison joins on the runner's registered IDENTITY (project, file, title path) rather than a runner-assigned test id, because a supervised run drives its own trusted config and the ids it runs tests under are not the ids the repository's config enumerates.
- `gateforge test-gates --chaos <seed>` makes rare response-order races show up ON PURPOSE, reproducibly. The witness observation proxy already sits on the request path of every witnessed test, so with a seed it releases each proxied app response on a seeded schedule: a delay in `[0, maxDelayMs]`, and — for requests sharing a route key inside one test session — the option of releasing a LATER response before an earlier one. Only timing moves: bytes, status, headers and evidence semantics are untouched. The schedule is a pure function of (seed, session identity, route key, k), so the same seed replays it exactly, and the run records it (`chaos: { seed, maxDelayMs, reorder, schedule }` in the report and in the sealed execution result) with `timing chaos: seed <n> (max delay <ms> ms, reorder on|off) — replay with --chaos <n>` as the text line. The recorded route key is method + pathname with the query stripped, so no credential can reach a report. `--chaos` is accepted only with `--result-only` and only against the witness the run spawns: a run whose timing was perturbed on purpose finds races, it never seals a receipt and never writes the run record. `run.chaos: { maxDelayMs, reorder }` only TUNES the bounds (default 400 ms, reorder on) and never switches chaos on — without the flag every byte of a run, report and execution result is unchanged.
- `gateforge test-gates` now BINDS the compiled behavior catalog to the witness it spawned (supervisor-authenticated `POST /runs/behavior-catalog`, immediately after the run-context bind): the catalog, the case assignments each test may execute (from `.gateforge/test-map.yml` `caseIds`, keyed by the supervisor-registered test identity), the complete `http.endpoint` route inventory in the `{}` shape grammar, and the engine-bundle authority-profile digest. A repository with no `behaviorPolicy` makes no call and its run is byte-identical; a refused registration fails the run with one plain line instead of leaving every behavior obligation silently unprovable. A CLI-spawned witness also loads the operator-provided trusted fixture/actor provider from `GATEFORGE_FIXTURE_PROVIDER` (a `fixture-provider.mjs`, or the directory holding it), so strong cases can mint fixtures and actor credentials engine-side; without it they still block fail-closed. The `webhook` engine-level end-to-end is now GREEN through the real CLI (valid signature accepted and recorded, forged signature rejected with the log unchanged, replay still one row, receipt sealed).
- Engine-level end-to-end suites for the `workflow` and `auth` namespaces (`packages/cli/test/workflow-behavior-e2e.test.ts`, `packages/cli/test/auth-behavior-e2e.test.ts`): the real CLI over a fresh fixture repository, the packs' own `example/workflow` and `example/auth` servers behind the loopback attestation proxy, the witness `test-gates` spawns itself, and post-suite verdict evaluation through `check --require-e2e`. Each namespace ships a pass and a fail variant, and the fail variant is the SAME example server with one documented defect patched into the copy the engine scans (the workflow transition guards removed, the auth tenant equality check removed) — so what the suites prove is that a rejected illegal write and a refused cross-tenant write are reachable `satisfied` with the engine-read snapshot unchanged, and that an application which accepts either one blocks with `BEHAVIOR_EFFECT_MISMATCH` and a non-zero exit. Both rejection cases ride on an engine-driven positive control (a legal transition; the tenant's own refund), so "unchanged" can never be satisfied by an application that simply never moves anything, and both suites read the sealed before/after snapshots themselves to show what the engine saw.

- `example/behavior` ships the pieces a fresh copy needs to drive its cases: an approved fixture/actor provider (`fixtures/fixture-provider.mjs`), an `x-gateforge-env-fingerprint` marker on the reference app (GF-13 attestation), a `snapshotScope` on the reviewed adapter (the witness deliberately refuses the candidate GET transport there, so the scope is read by the adapter's own engine-side fetch), and a `.gitignore` for the generated `.gateforge/test-gates/` run state that used to be committed and made every run refuse to start.
- Declared signature profiles for `engine-http` behavior cases (plan 2026-09-25 Phase 1). `signatureProfile` now takes an algorithm plus bounded `;key=value` parameters — `header`, `timestampHeader`, `toleranceMs`, `attemptHeader`, `attempt`, `forgery` — parsed by ONE grammar (`parseBehaviorSignatureProfile` in core) that the config schema and the witness request driver both use, so a typo is a config error and an unknown parameter never becomes a silent default. The secret still comes only from the trusted lease, the signature still covers the exact bytes on the wire, and a `forgery` is performed by the engine (one flipped digest nibble), never by the suite. A lease subject `signatureTimestampMs` lets a case declare a stale stamp, which the driver refuses when it falls outside the declared `toleranceMs`; over-limit bodies still never leave the driver. A bare `hmac-sha256` is byte-for-byte the previous behavior. Proven against the pack's own `example/webhook` receiver: a valid signature is accepted and the delivery log gains exactly one row, a forged signature is rejected 401 with the log unchanged, and a replay still leaves one row.
- `example/webhook/server.js` exports its `start` function for harnesses that own their own delivery-log state, and applies the side effect to THAT state (it previously wrote to the process-global log, so a harness-owned state never saw its own rows). It also serves a read-only `GET /delivery-log` listing.
- An engine-level end-to-end suite for the `webhook` namespace (`packages/cli/test/webhook-behavior-e2e.test.ts`): the real CLI over a fresh fixture repository, the pack's own `example/webhook` receiver behind the loopback attestation proxy, the witness `test-gates` spawns itself, and post-suite verdict evaluation. It compiles three owner-declared required cases (valid signature, forged signature, replay) and pins the CURRENT state honestly: the grader reaches all three webhook obligations and each one is `missing` with `BEHAVIOR_CASE_MISSING`, because no supervisor path binds the compiled behavior catalog to the witness, so the run's own failure artifact reads `no behavior catalog is bound to this run`. The example receiver gains a read-only `GET /delivery-log` listing so a reviewed adapter can witness the delivery log as a scope.
- The Status text in `README.md` and the capability table in `packages/cli/README.md` now match the code: `auth:*`, `validation:*`, `task:*`, `webhook:*` and `workflow:*` are registered semantic verifiers that grade across the approved required cases through the witness-issued `behavior.case` channel (they were still documented as fail-closed namespaces with no verifier). A repository that declares no case for such an obligation still blocks `missing` — the grader never falls back to transport evidence — so only the stale documentation changed, no verdict, cause code or exit code.

- Adapter kit `@gate-forge/witness/adapter-kit`: `defineHttpAdapter(config)` builds a contract-valid evidence adapter from a reviewed config (read/list paths, wrapper keys, projected fields, paging, a witness-side login seat). Paging is bounded and fails closed with `result truncated` instead of returning a partial list; a redirect-only read path fails closed naming its `Location`; credentials come only from named witness environment variables. Adapters without `volatileFields` behave exactly as before.
- `gateforge adapters check --probe` reads a kit adapter through the adapter's OWN seat (its login, cookie or bearer, one re-login on 401, GET-only) instead of an unauthenticated GET, so a collection only a logged-in session can read probes as `ok` rather than a 401 that blamed correct credentials. A seat whose witness environment variables are missing is reported as `the seat '<name>' needs <ENV_A>, <ENV_B> in the environment — not probed` (names only, never values); a rejected login names the login POST status. An adapter without `auth` is probed exactly as before.
- An adapter may DECLARE the fields the server computes itself (`volatileFields`). The witness stamps the declaration onto the persistence record, the exact-value echo skips exactly those keys, and the run reports every skip as a non-blocking `ADAPTER_VOLATILE_FIELD_SKIPPED` advisory. An undeclared key still fails the echo as before.
- `gateforge adapters scaffold [--dry-run]` writes one reviewable starting-point adapter per business resource that has none, from the compiled graph and the route inventory. It never overwrites, marks every guess in the file's own header, and prints a "needs you" list with the reason for everything it refuses to guess. `gateforge adapters check [--probe --base-url URL] [--probe-id ID]` loads and validates every adapter with the same contract validator the witness uses, reports the resources that still have none, and with `--probe` issues one read-only GET per adapter (ok / absent / auth / fingerprint mismatch / failed). `gateforge enforcement doctor` carries the same audit as one summary line.
- `CONNECT-YOUR-PROJECT.md`: the full zero-to-first-green-commit guide (stacks, `init`, test environment, runner, adapters, test map, first run, hooks/CI, single-test re-check, and the top ten problems the first integration hit), linked from the README and the quickstart.
- `gateforge enforce --ci gitlab|github --witnessed` writes a WITNESSED CI job template next to the static one (`.gateforge/ci/gitlab-witnessed.yml`, `.github/workflows/gateforge-witnessed.yml`): the lane that actually seals a receipt in CI. The job installs the pinned CLI, creates a private job-scoped workspace and stack/image names derived from the CI job id, forwards the merge-request base sha into the environment both supervised commands run in, runs `gateforge run -- --changed --scope full` so the app's own recipe owns the services, reads the verdict out of `report.json`, and uploads the report, receipt, execution result and the secret-screened `failures.json` as artifacts. The run prints straight into the job log, so the progress stream shows each test as it finishes. It never echoes a secret variable, and neither the recipe log nor the suite's raw output (which passes through the run and can carry the app's own secrets) is ever written to a file or uploaded. Templates are plain reviewable YAML, written only when absent; without the flag every generated file is byte-identical to what it always was.
- `gateforge run` performs a whole local witnessed proof in one command: a strict doctor preflight, the app's own optional recipe, the supervised `test-gates` with the user's flags, `check --require-e2e`, and the recipe's teardown — always last, after a failure too. It adds no authority: it only sequences commands the user could run, every verdict still comes from the same engine, one plain line per step carries its duration, and the exit code is the first failing step's own code (2 usage/config/recipe, 1 preflight or gate, the command's code for a recipe step, 124 on a step timeout). Recipe output is written to `.gateforge/test-gates/run-recipe/<step>-log.txt` and never to the console, because a recipe command may print secrets.
- An optional app recipe in `.gateforge/runtime.yml`: `prepare`, `reset`, `seed`, `services_up`, `healthcheck` and `services_down` steps, each an argv command list with its own `timeoutSeconds` and bounded `retries`, plus `env_files` (paths only — an inline `NAME=value` is a schema error, and the loaded values are never printed). The document is the same one the witnessed pre-commit staged runtime uses, extended additively; without it `gateforge run` starts and stops nothing and behaves exactly as before. An unknown key, a malformed step, or a missing env file is a plain exit-2 error — a half-understood recipe never runs.
- `gateforge enforcement doctor` reports a new read-only `run` section: verifier key location, the owner-approved policy pin (present and matching), the configured runner binary and its version, the configured interpreter paths, python bytecode safety, target reachability (only when a base URL is configured), the recipe healthcheck (only when a recipe exists), host load (advisory, never failing) and candidate-tree readiness — one PASS/WARN/FAIL line each with the exact fix command. The doctor stays report-only and exits 0 as before; `gateforge enforcement doctor --strict-preflight` exits 1 at the first failing precondition. The report gains only the additive `run` key.
- `GATEFORGE_CI_ENGINE_SOURCE` declares where the generated GitHub Actions workflow installs the engine from (a `.tgz` path, a directory, or any npm specifier), for a release that is not on the registry. Unset (the default), the generated workflow is byte-identical to before and installs `@gate-forge/cli@<version>` from the registry; set, the same workflow installs that one specifier through the step environment and records it in its header, and a value npm would read as a flag is refused with exit 2. The GitLab template is unchanged: it installs the repository's own declared `@gate-forge/cli` dependency.
- Optional owner-chosen gate strictness: `mode: strict|changed|warn` in `.gateforge.yml`. A missing key is `strict`, which is exactly today's behavior. `changed` blocks only on debt this change touches (the full debt is still reported); `warn` evaluates and reports everything and exits 0 with an additive `wouldBlock`. Exit code 2 (config/usage) is never softened, and the active mode is printed in every report and surfaced by `gateforge enforcement doctor`.
- `gateforge quarantine <testKey> --owner --approver --reason --expires` writes an owner-approved, always-expiring (max 14 days) flaky-test quarantine. A quarantined test leaves the required set, its outcomes and evidence are never used for any claim (an obligation only it covered stays `missing`), and it never blocks. An expired quarantine is ignored and blocks with `QUARANTINE_EXPIRED`. Quarantine files are part of the pinned trusted policy, so an agent-authored quarantine is a policy change that blocks until the owner repins.
- Goal-based `gateforge init`: one question (light / normal / strict) or `--preset light|normal|strict` maps a goal to the exact settings it writes and prints them, plus the `undo:` command. `gateforge init --explain-presets` prints the same mapping and writes nothing. With no terminal and no `--preset` (an AI agent or CI), init writes `light` only (`mode: warn`, no hooks) and prints that a human must choose; it never guesses `normal` or `strict`. A preset never writes a waiver, an adopted baseline or a plane rule, and an existing `.gateforge.yml` is never rewritten.
- The supervised spool drain exposes its own persistence-intent forward progress (`whenIntentsForwarded(count)`): it resolves once the witness has answered that many drained intents, so a caller can wait for the server-side probe to have run instead of guessing a number of poll ticks. It is the drain's own fact — the supervised suite only appends to the spool and can neither observe nor assert it — and it fails closed (rejects) rather than resolving on an unproven assumption.
- `gateforge test-gates --test <selector> --result-only` runs hand-picked tests witnessed, in seconds, instead of a whole suite. `--test` is repeatable and is accepted ONLY with `--result-only`: a hand-picked list never seals a receipt. A selector is a logical key or a unique substring of one, resolved against the planned rows (never raw runner output); an unknown or ambiguous selector exits 2 with the candidate keys listed. The named run uses the additive `named-selection` selection mode, so it can never collide with a full or scoped seal, and adds `selectors: [{ selector, logicalKeys }]` to the report. It works for every runner through the shared adapter contract.
- Opt-in `enforcement.reseal: true` lets `test-gates --changed --scope changed` re-seal after a test-only change: Gateforge diffs the two sealed trees itself, classifies every changed path from the runner's catalog and the repository import graph, re-runs only the tests the change can affect (importers of a changed file included) and carries the parent's outcomes. Eligible paths are test files and test helpers only; app code, a deleted file, a setup or dependency-stage test, or an unresolvable import falls back to the plain changed-scope run with one plain reason line. A complete whole-suite run that failed a test seals no receipt and leaves `.gateforge/test-gates/run-record.json` instead — a MAC'd, verdict-free run record the same path re-seals from when every test that did not pass is inside the affected set and passes now. The chain is bounded at 5 consecutive re-seals, and `check --require-e2e` and `broker commit` recompute every hop (parent authentication, tree diff, classification, affected set, carried rest) with their own keyring. Off by default in every mode; `enforcement.reseal: true` enables it in any mode, `strict` included. When the path is on and the run state holds a parent document it cannot re-seal from, the run says so in one plain line naming the first binding that failed — `test-gates: the previous run cannot be re-sealed from: its sealed tree is not the tree of commit 9c8a3b7 (uncommitted changes were tested) → changed-scope run` — instead of silently taking the changed-scope path. The parent is bound to the commit the parent DOCUMENT names, which must exist in the checkout and be an ancestor of HEAD — no CI variable is involved, and `CI_MERGE_REQUEST_DIFF_BASE_SHA`/`GITHUB_BASE_REF` are ignored, so a CI run must persist `.gateforge/test-gates/` between pipelines (a cache keyed by branch); with a cold cache there is no parent and the run is the ordinary run. With the path off, or with no parent document at all, the output is unchanged byte for byte.
- `enforcement.resealRuntimeFiles` lets the owner declare the runtime state the run itself rewrites inside the repository (a witnessed login stage's storage state, a runner cache) as repo-root-relative globs, so a re-seal is not blocked forever by gitignored bytes that differ between every pair of sealed candidate trees. A matching changed path is disregarded only when **neither** sealed commit tracks it — a committed path is source, whatever the glob reads, so a declaration can never hide a source change. The run prints one plain line (`test-gates: re-seal disregards 2 declared runtime file(s): …`), the re-sealed receipt keeps the real `changedPaths` and adds `resealDisregarded`, and `check --require-e2e` and the broker recompute that exact list from the same globs or reject the receipt as `EVIDENCE_STALE`. Absent by default: a repository that declares nothing is byte-identical, and it refused with `app file changed: e2e/.auth/contractor.json → changed-scope run` until the key was added.
- A dynamic import with a **literal** specifier is now an ordinary import edge instead of a refusal: `import('./x.mjs')`, `import("./x.mjs")`, `` import(`./x.mjs`) ``, `require('./x')`, `importlib.import_module('x')` and `__import__('x')` resolve like a static import, so the file that loads the module re-runs with every importer of what it loads. A **computed** specifier — a variable, a concatenation, a template with `${…}` — still refuses the re-seal, and a call with anything but a single literal argument is treated as computed (fail closed). Before this, one tracked file with `import('./master_session.mjs')` refused EVERY re-seal in the repository with `unresolvable import: … computed specifier`.

- A secret-free CI progress stream (`gateforge test-gates --progress stderr|file:<path>|off`, and the additive `run.progress` config key). It prints the start line with the registered expected-set size, one line per finished test with exact `N/M` counters and the test's catalog title, an alive line every genuinely quiet minute, and the finish line before grading. It is built from witness-side facts only — counters, identities, catalog titles, outcomes — and NEVER from runner output, so it is secret-free by construction; a failing test's first error line is matched against credential shapes and replaced whole. `auto` is stderr under `CI=true` and off everywhere else, so a local run's bytes are unchanged, and the stream is written only when it is on. It decides nothing: it is not evidence, no gate reads it, and a write failure warns once and is then ignored.
- A failing witnessed test ships a Gateforge-owned diagnosis instead of a browser snapshot: `.gateforge/test-gates/failures.json` carries each failure's logical key, its guarded error message and up to five `file:line` stack frames. No request or response body is ever included, and a planted credential in an error message reaches neither the stream nor the artifact.
- `execution.repositoryDebt` gained `baselined`, `newlyBlocking` and `notGradedBlocking` beside the frozen `blocking` total (which stays exactly as computed: repository blocking verdicts + repository findings), and the text summary now reads `repository debt: N known (baselined), M new blocking / …`. All of them come from ONE definition over the graded verdicts, so the text and the JSON can never disagree, and `M` is exactly what this run's exit code blocks on: a full run's whole surface, a changed- or named-scope run's own slice. Debt outside a slice run is reported with its own words (`not graded by this changed-scope run: K blocking obligation(s) — …`), never counted as new.
- `gateforge test-gates --help` documents `--progress`, and the run's scope is published to the in-runner reporter as `run-scope.json` (derived run state, read by nothing the gate trusts).
- Candidate-tree ingestion hashes and stores its objects in process instead of spawning `git hash-object` per file and `git mktree` per directory level. The tree id for the same bytes is unchanged, every object is still an ordinary loose object in the same authority store (so `git diff-tree`/`git cat-file` on the candidate tree are unaffected), the same files are hashed (gitignored ones and `node_modules` included — a swapped package still voids the receipt), and every fail-closed rule and message is unchanged. Ingestion now costs two git processes in total, whatever the workspace size.

### Changed

- A named or changed-scope run's in-runner reporter no longer prints a repository verdict it cannot own: it says `GATEFORGE GATE: SELECTION (N satisfied, 0 blocking; repository verdict not graded here)` instead of `NOT PASSED` over debt the run never observed, which contradicted the CLI exit code printed seconds later. A selection whose own claim is unsatisfied still prints `FAIL`; a whole-repository run is unchanged.
- One run can no longer show two different repository-debt counts. The in-suite Playwright reporter graded claims only, so its `N known (baselined) / M new blocking` split was a guess beside the gate's: a real run printed `412 known (baselined), 87 new blocking` from the reporter and `396 known (baselined), 0 new blocking` from the CLI for the same 519 obligations, while the CLI's own JSON said `blocking: 96` beside `newlyBlocking: 0`. The reporter now prints `repository debt: graded by gateforge after the run` and `run-summary.json` carries only its legacy keys (`obligations`, `unclaimed`, `blocking`), and the gate's `newlyBlocking` is the count it blocks on instead of the total minus the baselined count. The `debt-baseline.json` run-state view is gone: a baseline id list is not the gate's grading, so nothing derived a split from it.
- A changed- or named-scope run no longer reports repository debt it does not block on as `new blocking`: a real run exited 0 on three selected tests while the repository carried 96 `missing` obligations, and the line would have said `96 new blocking`. `newlyBlocking` is now exactly the count the run's exit code blocks on, and the untouched debt is named in its own line (`not graded by this changed-scope run: 96 blocking obligation(s) — this run never observed them; a full run grades them`). A full-scope run's numbers, and the frozen `blocking` total of every run, are unchanged.
- `tests discover` never narrows several Playwright configs silently: when a repo holds more than one, the runner line now names every config it found, the one enumeration ran, why that one, and the ones NOT inventoried (their test cases are missing from the catalog). The chosen config, the invocation and every field are unchanged.
- `enforcement doctor` no longer calls a tarball install the registry: its `engine:` line now reads npm's own install metadata (the owning `node_modules/.package-lock.json`, else the manifest's `_resolved`/`_from`) and says `from node_modules (tarball or directory install: file:… — not the published registry release, so CI installing @gate-forge/cli@<version> would NOT run this code)`, or `… (registry or tarball install — no install metadata found, so the provenance is unproven)` when there is none. A real registry install and a local checkout print exactly the lines they printed before. The receipt-bound `engine.source` keeps its meaning, so no receipt changes meaning and no receipt validity changes.
- Editing the repository's own `.pre-commit-config.yaml` is now announced as an action: `init --blocking`/`enforce` print one line naming the file as yours and the exact way back — `undo: git restore -- .pre-commit-config.yaml` for a tracked file, and (for an untracked one, which has nothing to restore) the line says to delete the appended entry instead of printing a command that would fail. The doctor's `hook-mutation` warning is now actionable in the order the owner meets it: it names those hooks as the repository's own and says to run `gateforge init --blocking` (or `enforce`) first, then move `gateforge-check` to the FIRST entry, instead of telling someone to reorder a hook they do not have yet. No file, exit code, or check id changes.
- The first real `next` on a FastAPI repository explains its owner question before asking it: one plain line says the route has no data plane, that no detector can read the answer from the code, and what each answer does (`tenant` / `master` / `global` → run only that `classify plane` command; a route no real user calls → the owner-only internal rule). The question itself, every printed command, the cause vocabulary and the exit code are unchanged; the `guidance` array gains that one line, before the question.
- Reports gained additive fields only, and only when they apply: `strictness` (non-strict modes) and `quarantine` (non-empty population). SARIF output stays machine-parseable JSON.
- `gateforge adapters scaffold` generates adapters that match a hand-written one far more often: a per-parent sub-collection (`/contracts/{contractId}/invoices`) is never sold as the complete collection (and never as a by-id read), route naming matches across `_`/`-` per whole path segment, `deletion` follows the graph's own soft-delete signal (a soft-delete-looking column raises a "needs you" line instead of a silent hard delete), and `fields` projects every column the graph declares for the table — the SQLAlchemy detector now reports `columnNames` — minus the primary key and credential-shaped columns, which the file header names.
- The adapter scaffold never projects a primary key as a business field, whichever layer declared it (the classification or the table's own `primaryKeyColumns`), and its header omits the `excluded:` clause when nothing was excluded.

### Fixed
- `gateforge next` no longer prints a command a user cannot paste. Every candidate `classify plane` command was followed by a bare, never-substituted `[CODE]` line, and the quickstart tells the reader to copy commands out of this output, so a shell fed that block ran `[CODE]` as a command. The marker is gone from the command block. The `gateforge init --planes` prerequisite is printed only while `.gateforge/planes.json` does not exist: it once claimed "run this once" above every route block, including after the file was there and every plane command had succeeded. The `[CODE]` fences that delimit a multi-line FILE-CONTENT block (a behavior declaration, an owner rule to paste into a config) stay: they bound the content, and no command is printed next to them.
- An `ENDPOINT_SEMANTICS_UNRESOLVED` block is now answerable from the output alone. It used to end in `do: gateforge discover --json` — a read-only dump that changes nothing, so the documented agent loop (run the printed command, run `next` again) repeated the identical block forever on any repository whose handlers delegate to a service layer. `gateforge next` now prints the owner-authored `.gateforge/endpoints.json` rule for THAT endpoint (its own method and canonical path as the selectors, the two owner-chosen fields marked, their allowed values named — `crud-archive`/`crud-delete` on a DELETE, the closed compiler vocabulary otherwise), plus the `gateforge explain` command that proves the declaration applied. The snippet is the product's own schema, so a rule filled in from it parses and resolves the block; a rule left with a placeholder capability still fails closed at startup (exit 2) with the allowed values. `--json` gains the additive `endpointSemanticsGuidance` array and keeps its existing fields, and a repository with no unresolved endpoint prints nothing new.
- The documented verifier-key ceremony now creates the key ring the product actually reads. `QUICKSTART` step 6 (and the same block in `TEST-ENVIRONMENT.md` and `UPGRADE-0.6-to-0.7.md`) told a user to create `$HOME/.config/gateforge/keys.json` and export `GATEFORGE_WITNESS_VERIFIER_KEY_FILE` for it, while `gateforge key create` with no `--file` writes `${XDG_CONFIG_HOME:-$HOME/.config}/gateforge/verifier-keyring.json` and every later command — including `enforcement doctor`'s `verifier-key` check — reads that path. On any machine with a non-default `XDG_CONFIG_HOME` (most CI images) the documented command therefore produced a ring nothing read, and a second `key create` was needed that no guide mentioned. All three guides now run `gateforge key create --confirm` alone, say which file that creates, and say that `--file` is for a ring that really lives elsewhere (with the matching export). The CLI README names the same default path.
- The example app's "Gateforge first run" now says how to install Gateforge. It started at `gateforge init` and the only install instruction anywhere in the example tree was an error string inside `behavior/scripts/gate.mjs` — so a user of the reference app had to guess both that a CLI install comes first and which packages the app needs. The section now installs the CLI, the Playwright pack and the HTTP pack (the two packs its own configs load, pinned to one release, with the `GATEFORGE_PACKAGE_INCOMPATIBLE` consequence named), and — for a release that is not on the registry yet — the one command that installs the WHOLE pre-publish tarball set (`npm i -D ./gate-forge-*.tgz`), because installing a subset is exactly what leaves npm fetching a missing package from the registry. It ends by naming the project-local binary (`node_modules/.bin` on `PATH`, or `npx`).
- The check and test-gates reports now print the engine provenance the enforcement doctor prints, so one install no longer produces two contradictory claims. A tarball or directory install lands in `node_modules` exactly like a registry release, so the doctor was fixed to name the truth while the reports kept claiming `engine: 0.7.1 from registry` for the very same repository — and the false claim is the one a consumer's CI reads. The report renderer takes an optional `engineLine` used by the TEXT format only, computed from the same npm install metadata the doctor's line is; the receipt-bound `engine.source` is unchanged (a receipt is only valid for the engine that sealed it) and the json and SARIF documents keep `engine` verbatim.
- The run's scope line now calls the expected set what it is. A full-scope run opened with `scope: full (62 mapped tests)` in a repository that has no test map at all and no obligation to mark — the number is the discovered CATALOG the run plans to execute, not a count of declarations, so the one number a user reads to check whether their `tests mark` took effect told them they had mapped 62 tests when they had mapped none. The line reads `planned tests` (the same word the runner's own selector diagnostics already use); its shape, the `--scope changed` advice and the rest of the line are unchanged.
- A `plugins[].version` that does not match the detector now names the field, both versions and the fix, instead of only the contract it broke. Adding a pack the documented way — by hand-editing `.gateforge.yml` — and copying a sibling entry's `version:` made every command exit 2 with `signal contract violated`, a line that named neither the field to edit, nor the value the pack's detector actually declares, nor how to obtain it (the pack's npm version and its detector version are different numbers, which is the whole trap). The boundary message now carries the remedy — `set version: '<declared>' on the '<id>' entry in .gateforge.yml, or run \`gateforge init --plugins <id>\` to write the pin the installed pack declares` — and a signal claiming a different detector ID (which no version edit can repair) says so instead. The exit code is unchanged, and `CONNECT-YOUR-PROJECT.md` now shows one complete, correct `plugins:` entry with the rule.
- `gateforge init` now recognises a SQLModel table whose base is declared through another class, so the canonical FastAPI template stops being read as a repository with no data layer. The scan's needle required `SQLModel` written literally in the class head, so `class UserBase(SQLModel)` + `class User(UserBase, table=True)` — the layout the template itself ships — produced no `sqlalchemy` signal at all: `init` recommended `pack-fastapi, pack-http` and never `pack-sqlalchemy`, the one pack whose proof channel that persistence layer needs, and the run it wrote had nothing to grade a model against. The scan now resolves the base chain: a `table=True` class whose base reaches SQLModel through classes the same module declares, or through a name imported from a module that declares a SQLModel class, is a model, and the printed reason quotes the class head it found (`class User(UserBase, table=True)` in `backend/app/models.py`). A chain that never reaches SQLModel is never promoted.
- `enforcement doctor` and the run preflight no longer call a browser cache ready when the browser builds the run would launch are not in it. A supervised run launches the CONSUMER's Playwright — the package that resolves next to its own config, usually a different release from the hoisted one — and each release pins its own browser revisions in the `browsers.json` of the package it launches. Both surfaces only counted cache ENTRIES, so on a machine where another project had already installed a different Playwright they reported `[OK] runner: playwright installed; browsers installed (N entries)` and the first witnessed run then failed EVERY test with `Executable doesn't exist at .../chromium_headless_shell-<revision>/…`. The `runner` line of both surfaces now resolves the runner exactly as the run does (`@playwright/test` first), reads its own registry, and checks the builds the config's projects would launch (each named `browserName`, chromium plus its headless shell by default, skipped when the config turns headless off). A missing build is a `fail` naming the exact `npx playwright install <browsers>` and the directory that must run it (the one holding the config, so a sub-project's own install is fixed in place); all builds present keeps the historical wording plus the verified build names; a runner that ships no readable registry keeps its exact previous line. `TEST-ENVIRONMENT.md` gains the matching checklist rule.
- The response-field advisory no longer accuses the two shapes that are not model reads (plan 20260925-2011 Phase 4b item 5, after a run on a real FastAPI + React app produced only false positives). (1) Error-envelope reads: a branch that opens on the call's own envelope is read for its POLARITY and only its failure arm is dropped, because the body a failure branch reads (`res.data?.detail`) is the server's error envelope, never the success model. `if (res.ok)`, `if (res.ok === true)`, `if (res.status >= 400)`, `> 399`, `!== 200`, `!== 201`, `< 400`, `=== 200`, `<= 299` and their negations decide which arm runs, so the SUCCESS arm keeps its reads — `if (res.ok) setItems(res.data.items)` is the most common success path and is exactly where a dropped field hides — and a read after an early-return guard is still reported when the success model dropped the field. A compound condition (`!res.ok || res.status >= 500`), a comparison the pass cannot read (`>= Math.min(400, limit)`) and a `statusText` test are undecidable, so both arms are dropped. A ternary is the same guard as an `if` (`res.ok ? res.data.items : res.data?.detail` keeps the success arm); a ternary on anything else is not a guard, so both of its arms are ordinary reads. Independently, `@gate-forge/pack-fastapi` now always declares `detail` among a route's wire names, because FastAPI's own error body is `{"detail": …}`, so even a stray `detail` read outside a guard is never flagged. (2) Fallback chains: a read that is one operand of a `||` / `??` chain now carries that chain's index, and the check judges the chain as the ONE decision it is — `res.data?.invoice_id || res.data?.invoice?.id` is silent when the model declares `invoice_id`, because `invoice` is its defensive fallback; a chain in which no operand is declared is still reported whole. Nothing about the advisory's blocking behavior, its exit code or the byte-identity of a repository with no gap changed.
- A run can no longer be sealed against a witness that perturbs its timing, and a witness too old for run options can no longer pass for one that honored them. A NORMAL run against an external witness that was itself started with `GATEFORGE_CHAOS_SEED` was silently accepted, so a perturbed run could produce a receipt nobody could replay; it is now refused before any test runs (exit 2, one line naming the variable to unset). A witness that does not echo the options it was given is refused for `--chaos` (it would apply no schedule while reporting as if it had) and prints one plain line for twin coverage (it recorded no shapes while reporting twins that agreed). A normal run against a witness with no chaos plan — including one too old to have the schedule route, which answers 404 — is byte-identical to before: no chaos label, no extra output, the same exit code.
- A test-only re-seal now survives the runs a pipeline does in between. The parent's evidence was read out of the LIVE run state when the re-seal decided, so the first thing that rewrote `manifest.json` — a consumer's materialization pre-step, which drops the witness attestation envelope while leaving `receipt.json`, `run-record.json`, `records.json` and `claims.json` in place — took the envelope away and the re-seal refused with `its evidence carries no witness attestation envelope → changed-scope run`, exactly where the path matters most. The run that seals a receipt or writes a run record now retains its own records, claims and witness envelope in `.gateforge/test-gates/reseal-parent/`, atomically, replaced by the next run that seals a document there and cleared with the document it belongs to; the re-seal authenticates that copy (run id, input digest, `evidenceAttestationDigest` and the MAC under the consumer's keyring) and never falls back to the live documents, so a missing or tampered copy refuses with the same plain line. The copy is written only with `enforcement.reseal: true`, so a repository without the opt-in is byte-identical; no released key, code, exit code or receipt field changed.

- `gateforge run -- --changed --scope changed` no longer fails its own final step. The run sealed a receipt for the changed slice, then closed with a whole-repository `check --require-e2e`, which demanded evidence for every obligation the slice never meant to cover. A scoped run is now checked at the scope it sealed (`check --changed --require-e2e`, and the step line says so); every other run is checked whole, as before.
- `gateforge run -- … --witness-url <url>` no longer breaks its own run in the preflight. With an external witness the target base URL is that witness's observation proxy, which counts every exchange and refuses the run-context binding once it has seen one; the preflight's reachability probe went through it, so `test-gates` then failed with `refused run-context binding (HTTP 409)`. With `--witness-url` the target line now reads `not probed` (the witness attests the target itself); every other run probes exactly as before.
- `gateforge run` no longer refuses a repository whose Playwright is installed next to its config in a sub-directory (an `e2e/` project with its own `node_modules`, nothing at the root). The strict preflight looked only from the repository root upward, so it failed `runner: playwright is not installed` on a project whose supervised runs worked, and `gateforge run` stopped before the suite. The preflight and the doctor's Playwright line now resolve the runner where the supervised run does: next to the Playwright config first (`@playwright/test` before `playwright`), then from the root. A repository with a root install reads exactly as before.
- `example/workflow/server.js` now answers every request. A path it does not route used to fall out of the handler with the connection still open, so any liveness probe hung instead of getting an answer — and the witness's startup attestation (`GET /` must present the environment fingerprint) timed out and failed the whole run with `adapter target presents no 'x-gateforge-env-fingerprint' marker`. Unrouted requests are now `404 {"error":"not found"}`, like the `example/auth` and `example/webhook` servers already were. Every routed path, status and body is unchanged.
- A test-only re-seal now carries the parent's WITNESS EVIDENCE, not only its outcomes: the parent run's records and claims are retained (bound to the parent run's attestation, authenticated with the run's own keyring) and graded as the union with the re-run's own evidence, so an obligation only a carried test proved stays `satisfied` and `check --changed --require-e2e` exits 0 after the re-seal. Attribution is by the witness-issued test id, so a re-run test's parent record never survives; the receipt binds the union in the additive `carriedEvidenceDigest`, and `check --require-e2e` and the broker recompute the union from the retained documents and fail closed (`EVIDENCE_STALE`) when the state evidence is anything else. Before this, every re-sealed run graded what only a carried test had proved as `missing` and the next check failed on evidence the parent run had actually witnessed.
- Consecutive test-only re-seals now work end to end: a re-seal is itself a whole-suite proof (it names the parent it carried from and seals a `coveredObligationFingerprints` list covering the repository), so it can parent the next one. The run state retains the chain hop by hop in `.gateforge/test-gates/reseal-chain/` — each hop's parent receipt, that parent's execution result, the catalog the classification used, and the witness-issued records, claims and attestations of every contributing run — and a test no hop re-ran keeps its original proof. Three defects are fixed with it: the parent evidence was written over hop 1 and then shifted into hop 2 paired with the wrong document, so a second hop's envelope named a different run; a run that sealed no receipt left the chain behind, describing the parents of a receipt that was no longer there; and the carried count double-counted a test an inner hop had re-ran while the deeper runs' records were never authenticated, so the untouched spec graded `missing` on evidence three runs had witnessed. `check --require-e2e` and `broker commit` now walk the whole chain, authenticate every contributing run's envelope with their own keyring, and check the chain's carried total once against the receipt of record (`re-sealed receipt claims N carried test(s) but its chain holds M carried outcome(s)`). Before this, the second consecutive re-seal left `check --changed --require-e2e` failing on the untouched spec, or refused outright.
- `pack-sqlalchemy` now sees SQLModel models: `class Item(SQLModel, table=True)` — and the split-base style `class User(UserBase, table=True)` over a shared `SQLModel` base — becomes a `sqlalchemy.table` resource named by SQLModel's own rule (the lowercased class name, new `tablenameProvenance` value `sqlmodel-class-name`), with its `Field(primary_key=True)`/`Field(foreign_key="…")` facts read as columns. The `SQLModel` root is recognized by import provenance (including aliases) and the same denylist vetoes the declarative rules use, and a `Field` call counts only when the file imports it from `sqlmodel`. A SQLModel class WITHOUT `table=True` (or with `table=False`) is not a table and is invisible in every channel, instead of claiming a name derived at runtime. Everything else about declarative detection, the unresolved codes, and the exit codes is unchanged.
- `--scope changed` in a merge-request CI pipeline with no base commit no longer falls back to the local staged diff (zero changed files, and a failure an hour later on debt nobody changed). `test-gates --scope changed` and `check --changed` refuse in seconds with exit 2 and the fix; an explicitly configured provider, a pipeline that is not a merge request, a present base commit, and every local run are unchanged.
- A run killed at the wrong moment (a CI container exiting while the witness shuts down) no longer leaves an empty `manifest.json`. The witness and the CLI write every run-state document to a temporary file and replace the old one by rename, so a later `check` sees the previous document or the new one, never a truncated file that fails closed with `no evidence attestation envelope found`.
- A consumer's Playwright config that prints at load time (a `dotenv`/`dotenvx` banner, a stray `console.log`) no longer breaks native test enumeration with "produced unparseable output". The JSON reporter's report is now read from the reporter's own output file — a channel stdout noise cannot corrupt — and is never guessed out of the child's output stream. When a run genuinely produces no readable report, the error says so and shows the runner's own output, instead of blaming the first stdout line.
- The pack's own pinned `playwright` no longer outranks the consumer's `@playwright/test`, so enumerating a project whose runner version differs from the pack's pin works instead of dying with the two-versions-of-@playwright/test conflict. The consumer's runner CLI is resolved from the config file's directory upward (nearest install first, `@playwright/test` before the bare `playwright` pin), and the pack's pin is the fallback. When a real version conflict survives that, the reported cause names BOTH versions and says what it is, instead of a "missing test dependency" that nothing is missing for.
- A checked-in symlink whose target does not exist yet (a link into a virtualenv the project has not bootstrapped) no longer makes `next` and `check` exit 2. The link is captured exactly the way git records it — a `dangling-symlink` entry bound to its link text alone, never followed and never read — so the run continues and one plain `note:` line names the link and its target. The entry still moves the evidence digest: retargeting the link, or the target appearing after the bootstrap, changes its identity and its type. A symlink that escapes the repository and a submodule still fail closed exactly as before.
- A checked-in symlink whose target is a DIRECTORY (the same virtualenv-skill shape, once the project's own bootstrap has run) no longer makes `next` and `check` exit 2 either. Such a link is captured the way a dangling one is — a `directory-symlink` entry bound to its link text alone, never walking the target, which can be an entire virtualenv — and one plain `note:` line names the link and says no action is needed; a dangling link's line now carries its fix as `do:` text. The entry moves the evidence digest when the link is retargeted and when the target becomes a regular file. A link escaping the repository, a link to a fifo/socket/device, and a submodule still fail closed exactly as before.
- Every `gateforge next` action is runnable as printed. The plane-classification guidance for an endpoint with no resolved plane prints `gateforge init --planes` FIRST, because the `classify plane` command below it exits 2 without the owner-reviewed `.gateforge/planes.json`; the single printed action could therefore never succeed. `init --planes` now honors an explicit `--planes` on a repository the language scan does not read as Python (it used to be a silent no-op there, which is exactly where the guidance is printed), and it writes the reviewed file even when no rule can be inferred — a file with zero rules declares no plane, which is what the classifier already assumes while the file is absent. Inference still never guesses, and an existing reviewed file is still left untouched.
- `init --plugins` on an already-initialized repository now does what the tip printed by every `init` promised: it ADDS the requested bundled detectors to `.gateforge.yml`. The merge is additive — an entry that is already there keeps the owner's own version pin, transport and module, nothing is ever removed, and every other key, comment and edit in the file is preserved. The merged document is checked against the pinned config schema before anything is written, and the run prints exactly which detectors it added. A config with no `plugins:` list to add to is refused with the shape to write by hand, never silently ignored.
- A non-blocking mode no longer prints a bare `exit code: 1` while the process exits 0. The text report's own exit-code line always carries the strict result, so when a mode softens it, the line is now labelled `would exit 1 in blocking mode` — the same fact, named as what it is — and a CI log or an agent reading the report can no longer read it as the process's code. `strict` mode keeps the exact line it always printed, the JSON document is unchanged (it already carried `strictness`), and every exit code is unchanged.
- The static test scanner no longer reports a false `EISDIR` parse error against a consumer's own source when a file and a directory share a name (`src/client/` next to `src/client.gen.ts`, imported as `./client`). Specifiers now resolve the way node/TS resolve them — a regular file first, then a directory's `index.*` — and a path that is not a regular file is never read as one, so such a repository no longer flips to an incomplete inventory.
- `gateforge init` recommends the detector packs the repository actually shows evidence for. A SQLModel table model (`class Item(SQLModel, table=True)`, the canonical FastAPI-template model style the declarative-base needles never matched) and a generated API client (a generator banner or generated-client runtime import in a js/ts file, or a shared `axios.create` instance) now produce the `sqlalchemy` and `http-clients` signals that recommend `pack-sqlalchemy` and `pack-http`. Evidence is read from file text only — a directory merely named `client` justifies nothing. Every recommended pack is printed with one `why:` line naming the concrete file evidence behind it, and a pack in the list only because of the language default says so.
- A headless `gateforge init` (an agent or CI) states its goal choice ONCE. The written preset and the flag that changes it now travel on one line — `no terminal: writing the light preset (report everything, block nothing) — a human must choose the goal: re-run with --preset <light|normal|strict> …` — and the closing summary no longer restates the same choice twenty lines later in different words. What the run wrote (`mode:`, hooks, `undo:`) is still reported, an existing `.gateforge.yml` still gets the "kept your own config" wording on that one line, and the goal table and an owner-chosen preset are unchanged.
- The files `gateforge init` scaffolds now point only at files a consumer install actually has. The overlay README's fixture shape was `example/e2e/accounts-crud-journey.spec.js` — a path inside the Gateforge monorepo, shipped to nobody, so the one scaffolded file that explains how to write a proof test pointed at nothing. `@gate-forge/pack-playwright` now ships `examples/overlay-proof.spec.js`: a complete, runnable proof test with a full surface descriptor and the witnessed `evidence.ui.*` → `visible.confirm` → `http.observe` → `persistence.verify` → `finalize` sequence, and the scaffold names it at its installed path. The two setup guides `GATEFORGE.md` names are given the same treatment (`node_modules/@gate-forge/cli/guides/…`, the layout the CLI package ships). A test now resolves both scaffolds' named paths against the real packed tarball layouts (`npm pack --dry-run --json`), so a path that stops shipping breaks the suite instead of a first run.
- The shipped docs name only commands and flags that exist. `gateforge init --help` now lists the negative forms the parser has always honored — `--no-blocking`, `--no-pre-commit`, `--no-planes` (alongside the existing `--no-ci`) — so the `--no-blocking` in `example/README.md` is a documented flag rather than a mystery that merely exits 0, and the CLI README's `init` row lists the same set. `guides/RUNNER-NEUTRAL-EVIDENCE.md` no longer tells a reader to run `gateforge doctor` (no such command; it exits 2 with `unknown command 'doctor'`): it names `gateforge enforcement doctor`, whose `runner` check really does report what the guide claimed — the `vitest`/`cypress` config file and installed package, an installed `playwright`, or a configured `diagnostics.suites` entry plus `pytest` on `PATH` — and states that it is diagnostic-only (exit 0 either way). `example/README.md` gained a "Where the witnessed run lives" section: the root project is the static-`check` demo (with the exact `check --require-e2e` no-receipt line), the witnessed project is `behavior/`, and its `tests discover` / `tests suggest` / `test-gates --changed` commands are given with their observed output — including that the run does not seal a receipt in a fresh copy today and prints a `gateforge explain <test>` line per failing test.
- Route attribution in the behavior grader no longer fails on a host's own parameter spelling. The compiled route inventory carries each endpoint's path in the framework's grammar (Express `:id`, FastAPI/Next `{id}`), but the grader's positional matcher only understood the engine's own `{}` slot, so a witnessed `POST /admin/accounts/acc-3` never resolved against the declared `POST /admin/accounts/:id` and every effect proof for such a route came back `invalid` with `BEHAVIOR_BINDING_MISMATCH` — a silently unprovable route, not a fail-closed one. `pathMatchesShape` now treats `{}`, `:name` and `{name}` as the same single-segment slot (still positional, still case-sensitive, never zero or many segments, `{*}` still trailing-only), which is the same normalization the witness-side route registration already performed. Literal, wildcard and ambiguity behavior is unchanged.
- `example/behavior` now gates green on a fresh copy with ONE command: `npm run gate` picks a free loopback port, creates a runtime verifier key ring outside the repository (mode 0600, in the OS temp dir, contents never printed), starts the reference app, runs `tests discover` + `test-gates --changed` + `check --require-e2e`, stops the app, removes the key ring, and exits with the check's status. This closes the last setup gap in the example: a supervised `test-gates` run never loads the consumer Playwright config, so its `webServer` never started the app and the app, the fingerprint, the fixture provider and the verifier key all had to be wired by hand.
- The behavior reference app declares and proves every route it exposes, so a fresh copy reaches `10 obligation(s) — 10 satisfied` and a sealed receipt instead of 20 blocking entries. The seven read routes are declared as `http:read-result-verified` cases that each drive their OWN route (the engine re-resolves every observed path against the declared endpoint, so a case that reads a different route is correctly rejected), not as dispositions or waivers. Its read handlers now name the resource they serve (`accountsListApiHandler`, `importAccountsCreateHandler`, …), which is the handler-name evidence the endpoint compiler requires before it will link a route to a business resource — name coincidence alone never links, so the previous names blocked with `ENDPOINT_RESOURCE_LINK_UNRESOLVED`. The engine-side fixture provider is excluded from the product scan scope in both `.gateforge.yml` and `classification-policy.yml`: its HTTP calls provision fixture subjects, and classifying them as product frontend reported the engine's own traffic as unresolved application call sites.
- Witnessed observe evidence no longer goes ambiguous when two tests create the same resource at the same time (parallel test files/workers are the normal case). A create is now attributed to the entity its OWN proxied response named, verified against the witness's after-list, so concurrent observed creates each resolve their own entity. A new entity that no observed response names — a writer outside the observation proxy — still makes the creation ambiguous and the obligation stays blocking; the unobserved-writer case is unchanged and fail-closed.
- A vitest project's second test of a file no longer waits for the runner's main process to report the first one. The end of a test now reaches the drain from the worker that ran it — in the same order as that worker's own begin — which releases that worker's session slot; the runner's own end still seals the session with the observed outcome, and only the runner ever states a verdict. A release credits nothing: submissions and the session proxy stop at the release, an outcome that never arrives leaves the session outcome-less (it grades not-passed), two different outcomes for one test are a lifecycle conflict, and an outcome with no begin still fails closed.
- A `--scope changed` run no longer blocks on affected obligations the run's own grading forgives through the adopted baseline: they are reported in one line (`N affected obligation(s) have no declared mapping and are forgiven by the adopted baseline; they stay uncovered by this slice`) and stay inside the sealed covered set, so `check --require-e2e` still demands what the full path grades. An obligation the baseline never adopted still blocks (shrink-only, fail closed), and strict E2E forgives nothing, so its behavior is unchanged. Before this, a repository that had adopted its unmapped obligations could not run a changed slice at all: the same debt the full run forgave blocked the narrow one with `EVIDENCE_SCOPE_INCOMPLETE`.
- Every re-seal refusal line now ends in what actually happens next: `→ changed-scope run`. The re-seal path is attempted only under `--scope changed`, so a refusal always falls through to the ordinary changed-scope run (a `scope: changed` receipt), never a full run. Before this, each refusal claimed `→ full run` while the run continued through the plain changed-scope path.
- The re-seal import scan no longer refuses on things that load nothing: a source file with non-ASCII text is read in full (object sizes are bytes, and the batch is now cut by bytes, not characters — before, the next file's header leaked into it and it "did not parse"), a local re-export `export { x };` is not an import, and a computed Python import only matters when a Python file changed (and a computed JS/TS import only when a non-Python file changed), because imports never cross that boundary. A real computed specifier in the changed file's language family still refuses, and a missing or truncated object in the batch now refuses instead of reading as an empty file.

## 0.7.0

### Added

- Added existing-test discovery, suggestions, declarations, and the `gateforge tests surface-doctor` diagnostic.
- Added `gateforge key create|import-env|rotate|retire` for external verifier-key rings.
- Added `gateforge test-gates --changed --scope changed --result-only`; external-witness runs require a separate non-authoritative `--out` and never touch receipts.

### Changed

- `check` combines `.gateforge/test-map.yml` with optional `claimInventory` from a receipt authenticated for current inputs; `claims.json` alone does not declare claims.
- Docs exclusions use exact repo-relative folders via `gateforge init --docs-exclude`; a matching external `GATEFORGE_APPROVED_POLICY_DIGEST` is required, and recognized manifest/lockfile basenames remain protected.
- Trusted Playwright configuration maps `appBaseUrl` to `use.baseURL` and `storageState` to `use.storageState`.
- The Playwright package guard checks the supervised protocol contract and returns exit 2 with `GATEFORGE_PACKAGE_INCOMPATIBLE` on mismatch.
- `init --blocking` installs and verifies an active pre-commit hook and writes CI gate wiring.

### Fixed

- A linked raw/witnessed twin pair that ran but could not be compared is no longer silent. When one side sent no request through the witness — most often a raw twin written as a plain Playwright test, which opens no witness session — the run prints `test-gates: twin pair not compared: the raw test '…' sent no request through the witness` and how to make it observable (run the raw twin with the Gateforge test fixture), instead of reporting no divergence as if the twins agreed.
- A flag given three or more times keeps every value. `test-gates --test a --test b --test c` used to fuse the first values into one comma-joined selector (`'a,b'`), so naming three or more tests always failed with `TEST_SELECTOR_UNKNOWN`; the same applied to every other repeatable flag.
- Installing `@gate-forge/witness` no longer pulls in `bullmq` and `ioredis`, and loading it no longer needs them. The queue observer imported them at load time, so every witnessed run of a project without them (every project without a queue) died at start with `Cannot find package 'bullmq'`. They are now optional peers, loaded only when `.gateforge.yml` declares `queueObserver: { kind: bullmq }`; a project that declares it without them fails closed with the install command.
- The shipped `example/` project checks clean again with its new `webhook/` sub-project: that sub-project's engine-side modules (its evidence adapter, gate script and fixture provider) are excluded from the frontend call scan, like `behavior/`'s.
- The twin title convention now links the way pairs are usually written: `X [witnessed]: <what it proves>` next to `X raw: <what it does>`. Before, only an exact `X raw` (or a bare `X`) title linked, so a suite that labels both sides and then describes each one got no twin comparison at all and had to spell every pair out with `twinOf`. An exact `X raw` still wins; two described raw tests under one label link nothing (the owner names that pair with `twinOf`).
- A test-only re-seal now carries the evidence of natively claimed tests. Their records are stamped with the id the runner gave the test while it ran, which is not the enumerated catalog id when the trusted config lives in another directory, so the carry matched none of them: the re-sealed receipt said `carriedEvidence: true` while it carried no parent record, and `check --require-e2e` reported every carried test's obligations `missing` (it never passed wrongly). The execution result's outcomes now keep the runner's own id in the additive `runnerTestId`, and the carry uses it next to the logical key and the catalog id. A re-run test's parent records still never survive.
- Witness startup waits for the reported proxy URL before proceeding.
- Fixed a shared-distribution witness spool race between concurrent runs.
